# Pre-Dev Alignment — 开发前对齐（前后端统一版）

你的任务是在开发开始之前，通过结构化对话帮助用户和你自己都真正理解这个需求——而不仅仅是执行表面的指令。

好的开发计划来自好的问题，而不是来自对需求的字面理解。你的目标是暴露隐含假设，发现真正的业务目标，识别技术风险，最终输出一个双方都认可、**且落档可追溯**的开发计划。

---

## 技术栈判断（前端 / 后端）

在进入任何流程之前，首先判断这是**前端需求**还是**后端需求**（或两者兼有）。

### 判断方法

**1. 关键词信号推断**

| 技术栈 | 典型关键词 |
|--------|-----------|
| **前端** | 页面、组件、表单、列表、弹窗、样式、布局、路由、菜单、tab、按钮、交互、UI、搜索条件、i18n、国际化、响应式、图表、dialog、drawer、select、table |
| **后端** | 接口、API、Service、Entity、数据库、字段、表、查询、gRPC、proto、domain、Flow、缓存、锁、权限、鉴权、token、SDK、Controller、QueryChain |

**2. 项目结构分析**

- 需求涉及 `src/views/`、`src/components/`、`src/router/`、`src/stores/`、`src/locales/` 等前端目录 → **前端**
- 需求涉及 `domain/`、`integration/`、`interfaces/`、`support/` 等后端目录 → **后端**
- 用 Glob 和 Grep 检查需求提及的文件或模块属于哪个技术栈

**3. 上下文推断**：用户提到的文件后缀（`.vue`/`.ts` vs `.java`）、模块归属、当前工作目录。

| 结果 | 处理方式 |
|------|---------|
| **明确前端** | 按前端流程走对齐（前端风险检测、前端检查清单、frontend skill 链路） |
| **明确后端** | 按后端流程走对齐（后端风险检测、后端检查清单、backend skill 链路） |
| **前后端联动** | 两栈检查都做，计划中分别列出前端和后端的实现步骤 |
| **无法确定** | 向用户确认："这个需求主要涉及前端还是后端？" |

## 任务分级

用户通常会在提出任务时直接标注级别。如果没有标注，根据以下标准自行判断：

| 级别 | 后端典型场景 | 前端典型场景 | 特征 |
|------|--------------|--------------|------|
| **L1 轻量** | 改配置、加字段、修 typo、调整返回值 | 样式微调、文案修改、单组件属性调整 | 影响范围单一，方案显而易见 |
| **L2 标准** | 新功能、Bug 修复、单业务域重构、接口设计 | 新组件/新页面开发、交互逻辑、表单联动 | 有业务逻辑，存在多种实现路径 |
| **L3 重量** | 架构调整、跨业务域重构、系统设计、性能优化 | 跨页面重构、全局状态改造、设计系统调整 | 影响范围广，决策有长期影响 |

**例外**：纯粹的小修改（改一个明显的 typo、改一个变量名）无需进入对齐流程，直接执行。

> 任务分级（L1/L2/L3）决定**对齐的深度**与**编码前的文档/评审门禁**；`dev-session` 的变更分级（ARCH/NORMAL）决定**编码后开发者评审的深度**。L3 通常对应 ARCH。

**分级 → 编码前文档产出 → 评审门禁**（本 skill 核心约束）：

| 级别 | 编码前文档产出 | 评审门禁（编码前，按顺序） |
|------|----------------|----------------------------|
| **L1** | 简化计划（可不落档） | 用户确认方案即可 |
| **L2** | **技术设计文档**（落 `design/`） | **开发者**技术审核 + 二次评估 → 通过才编码 |
| **L3** | **需求/调整文档**（落 `plan/`）→ **技术设计文档**（落 `design/`） | ① **用户**复核需求/调整文档（确保需求最终对齐）→ ② **开发者**技术审核 + 二次评估 → 通过才编码 |

- **需求/调整文档**回答 *做什么 / 为什么*（业务目标、范围、验收）——交**用户**复核，确认需求方向正确。
- **技术设计文档**回答 *怎么做*（技术方案、复用、实现步骤、影响面）——交**开发者**技术审核与**二次评估**（在需求初评之上，对方案合理性 / 工作量 / 风险 / 影响面再评一次），通过前不写业务代码。
- 两类文档、两道门禁、两个评审视角：L2 只需技术门禁；L3 需求门禁在前、技术门禁在后，顺序不可颠倒。

## 标准执行流程

### 第零步：场景分类与风险预判（提问前必做）

**0.1 判断开发场景**

| 场景 | 定义 | 流程差异 |
|------|------|----------|
| **A：新项目/全新功能** | 无现有代码可参考 | 完整走架构设计 → 编码 |
| **B：旧项目新功能** | 已有项目下新增业务域或页面/模块 | 必须先读同业务域/同模块代码，保持风格一致 |
| **C：旧项目迭代调整** | 对已有功能/接口/页面的修改 | 必须做影响面分析，外科手术式修改 |

判断方法：后端用 Glob 检查 `domain/{业务域}/` 是否已存在；前端检查 `src/views/{模块}/` 与路由配置；用 Grep 搜索同类功能的现有实现。

**0.2 关键风险检测**

扫描需求描述中是否包含以下关键风险点：

**后端风险关键词：**

```
权限/鉴权：permission、auth、role、token、login、oauth、jwt
账户/用户：user、account、tenant、租户
支付/资金：pay、payment、transaction、order、settlement
数据安全：encrypt、decrypt、密钥、敏感数据、cipher
跨业务流程：跨业务、cross-domain、multi-service、flow
数据库 DDL：建表、加字段、改字段、迁移
缓存/分布式锁：cache、lock、redis、分布式锁
gRPC 契约：proto、grpc、stub
```

**前端风险关键词：**

```
全局状态修改：store、pinia、global state、全局状态
路由/权限控制：route guard、路由守卫、permission、菜单权限、动态路由
公共组件修改：公共组件、common component、shared、全局组件
第三方库接入：sdk、第三方、external library、插件、编辑器
国际化变更：i18n、locale、国际化、多语言
大范围样式改动：主题、theme、CSS变量、全局样式、design token
跨页面数据流：跨页面、跨模块、event bus、provide/inject、全局事件
性能敏感场景：大数据量、virtual scroll、lazy load、大表格、无限滚动
```

命中任何关键词 → 标记为 **HIGH RISK**，后续流程强制附加：
- 风险评级不可降级；计划必须包含回滚方案
- **后端**：提醒需考虑灰度/双写/兼容性；DDL 变更确认 TableDef 同步方案（`tabledef` skill）
- **前端**：提醒需考虑公共组件影响范围、全局状态副作用、浏览器兼容性

**0.3 侦察上下文**

在向用户提问前，先主动收集信息：

- **沉淀检索**：读 `.document/developer/memory/MEMORY.md` 命中相关约束（feedback 强约束必读全文）；读 `.document/developer/capability/CAPABILITY.md` 确认**可复用能力**（组件/工具/流程/接口）——能复用的列入方案，不重复造轮子
- 阅读涉及的代码文件，了解现有实现；查找相似功能或历史方案；识别依赖关系和影响范围
- **后端（场景 B/C）**：读取同业务域的 Entity / Service / Controller / Operate / Query 代码风格
- **前端（场景 B/C）**：读取同模块的页面结构、组件拆分方式、命名规范；检查可复用组件

用**具体发现**引导对话，而非抛出空泛问题。能自己推断的不问用户。

### L1 轻量级流程

1. **一句话复述**理解，直接给出方案（含技术栈/场景判断结果）
2. **单轮确认**：只问有真正歧义的点（最多 1 个问题）
3. 在当前会话提交计划或文档供评审，写**简化计划**（背景 + 方案 + 验收，3-5 行）
4. 等待用户 Review → 对齐后执行

### L2 标准级流程

**第一步：快速理解 + 定向提问** — 一两句话复述理解，告知技术栈/场景/风险预判结果，选最重要的 2-3 个问题：

- **业务目标（Why）**：解决什么问题？成功标准？（前端：核心交互是什么？）
- **技术方案（How）**：有没有更简单的方式？**有无可复用能力（0.3 已查册）**？后端归属哪一层？前端复用还是新建？
- **范围边界（What exactly）**：必须做什么？可推迟什么？验收条件？

**第二步：深入追问** — 挑战"想当然"的假设；后端暴露层间依赖/跨域写操作，前端暴露状态管理/组件通信/异常空状态；区分真实需求和偏好（"这是必须的，还是 nice-to-have？"）。每轮不超过 2 个问题。

**第三步：给出建议** — 推荐方案（含层归属/组件拆分 + 复用清单）、潜在风险、替代方案及权衡、待确认疑点。

**第四步：输出技术设计文档 → 开发者评审门禁** — 先写出可审阅的技术方案，按下文「技术设计文档模板」写出技术方案，通过当前会话提交文档并在需要时等待确认 交**开发者做技术审核 + 二次评估**（方案合理性 / 工作量 / 风险 / 影响面）。通过后落档到 `design/`，再进入编码（L2 无需单独的用户需求复核门禁——需求已在前三步对齐）。

> **前后端联动 / 对外接口的需求多一个停顿点**：接口列表设计完后**先停一次**，输出接口摘要（方法 + 路径 + 关键入参出参 + 跨域依赖）等开发者确认，再写其余章节与任务拆分——契约是两端并行的前提，定晚了两端一起返工。确认后的契约写入技术设计文档「契约」章节冻结。

### L3 重量级流程

L3 在编码前分**两道门禁、两份文档**（顺序不可颠倒）：

**门禁一 —— 需求/调整文档（交用户复核）**：先把需求/调整意图写成**需求/调整文档**（模板见下），在当前会话提交计划或文档供评审交**用户**复核——确认业务目标、范围边界、验收标准最终对齐。用户确认后落档到 `plan/` 对应模块文档（新需求新建，迭代调整追加「迭代记录」）。需求未对齐前不进入技术设计。

**门禁二 —— 技术设计文档（交开发者技术审核 + 二次评估）**：需求对齐后，在 L2 技术设计基础上额外增加 **系统影响评估**（所有受影响的业务域/模块/接口/数据流）、**风险分级**（高/中/低 + 缓解措施）、**长期影响**、**不可逆决策标记**，并包含完整**决策记录（ADR 格式）**。在当前会话提交计划或文档供评审交**开发者**做技术审核与二次评估，通过后落档到 `design/`（重大架构决策另落 `adr/`），再进入编码。联动需求同样先停一次确认接口契约（同 L2 第四步）。

## 文档模板

> 按分级选模板：L1 用简化计划；L2 产出**技术设计文档**（交开发者技术审核 + 二次评估）；L3 先产出**需求/调整文档**（交用户复核）再产出**技术设计文档**（交开发者技术审核 + 二次评估）。

### L1 简化计划

```markdown
# [需求名称]
**技术栈**：前端 / 后端 / 联动　**场景**：A/B/C　**风险**：LOW/HIGH
**背景**：[1-2 句]　**方案**：[做什么]　**验收**：[怎么确认]
**落档**：[plan 文档路径或"轻量不落档"]
```

### 需求/调整文档模板（L3 必产，落 `plan/`，交用户复核）

> 回答「做什么 / 为什么」，交**用户**复核确认需求最终对齐；不含技术实现细节。新需求新建模块文档，迭代调整追加「迭代记录」小节。

```markdown
# 需求/调整：[需求名称]

## 基本信息
- **技术栈**：前端 / 后端 / 前后端联动　**类型**：新需求 / 迭代调整　**风险等级**：LOW / HIGH（命中：xxx）
- **台账条目**：{yyyy-MM-dd}_{stage}_{slug}

## 背景与目标
- **业务问题**：[解决什么问题，影响哪些用户/场景]
- **成功标准**：[如何判断完成且达到目标]
- **本次调整**（迭代场景）：[相对现状改了什么、为什么]

## 用户故事
- 作为 {角色}，我希望 {行为}，以便 {目的}（每个独立操作一条；角色即操作者，决定下面的权限场景）

## 范围边界
- **本次包含**：[功能点]
- **本次不包含**：[排除项 + 原因]（推迟 / 砍掉的同步落 `plan/backlog-{topic}.md`，见 progress-tracker）

- [ ] {正常路径 1}
- [ ] 异常场景：{错误输入 / 边界情况的预期行为}
- [ ] 权限场景：{不同角色操作的预期结果}（涉及权限时必填）
- [ ] 幂等：重复提交同一请求结果与首次一致（写操作必填）

## 边界与约束
| 维度 | 预估 | 对设计的影响 |

| 数据量级 | {单表预估行数} | {分页 / 索引 / 归档} |

| 隔离维度 | {多租户 / 组织 / 国家 / 无} | {查询是否必须带隔离字段} |
| 跨端接口 | {接口数} | {契约在技术设计文档「契约」章节冻结} |

## 风险与依赖
| 风险 | 等级 | 应对 |
|------|------|------|
| {跨域依赖 / 数据迁移 / 契约变更影响另一端 / 第三方 / 不可逆操作} | 高 / 中 / 低 | {方案} |

## 待确认事项（需求层）
- [需求/范围上仍需用户拍板的点]
```

> - **决策记录（ADR）**：方案选择的完整推理链（背景 / 选项与权衡 / 决定 / 后果），重大决策同步落 `adr/`

### 视觉交互 DEMO（按需，落 `design/`）

当**用户要求做视觉交互方案设计**，或属于**全新、无现成参照的视觉 / 交互**时，在技术设计阶段额外产出可看的 DEMO，供用户确认视觉与交互方向：

1. **优先复用既有组件**：前端已有可复用组件能拼出方案的，直接在前端项目里用既有组件搭 DEMO 页（走 `view-conventions` 与项目设计系统 token），不另起 HTML。
2. **HTML 原型**：无现成组件可复用、或需快速探索多套视觉时，产出独立 `{slug}-demo.html`（内联样式/脚本，用项目设计系统 token 占位）放 `design/`，作为评审与后续实现的视觉基准。
3. **方案定稿后**：由 AI 判断该视觉 / 交互是否值得**抽为可复用组件**——值得则按 `view-conventions` 落地组件并登记 `CAPABILITY.md`（跨项目通用的标「待反哺 framework」）；不值得则在正式开发中按 DEMO 实现即可。

> DEMO 是**编码前的方案验证载体**，区别于 dev-session P3「前端两轮」中基于 MOCK 的**真实页面实现**——DEMO 先定方向，MOCK 轮再落地。

## 对齐结论落档（每道门禁通过后立即执行）

**口头对齐不落档 = 未对齐。** 各类文档在对应评审门禁通过后、写第一行业务代码前落档：

| 内容 | 落档位置 | 规则 |
|------|----------|------|
| 需求/调整文档（L3 必产；用户复核通过后） | `.document/plan/{编号}-{模块}.md` | 新需求新建模块文档（含任务 checkbox 清单）；既有模块的迭代追加「迭代记录」小节。L2 同样在此登记需求载体与 checkbox 清单 |
| 技术设计文档（L2/L3 必产；开发者技术审核 + 二次评估通过后） | `.document/design/{yyyy-MM-dd}_{slug}-design.md` | 技术方案 + 开发前检查清单 + 实现步骤；L3 含系统影响评估 + ADR 章节 |
| 视觉交互 DEMO（按需） | `.document/design/{slug}-demo.html` | 用户要求视觉方案 / 全新无参照视觉时产出；定稿后判断是否抽为复用组件并登记 `CAPABILITY.md` |
| 砍范围 / 推迟的功能点（按需） | `.document/plan/backlog-{topic}.md` | 对齐中主动砍掉或推迟的 Phase / 功能点，按 `progress-tracker`「backlog 文档」格式当场落档，台账与需求文档只放指针——推迟不落档 = 遗忘 |
| 测试用例文档（dev-session P5 产出） | `.document/design/{yyyy-MM-dd}_{slug}-testcases.md` | P5 自测前产出（TC 正常/边界/异常/回归范围 + 执行记录），P6 随 Review 材料确认，P7 据此验收 / AI E2E；轻量任务可内联在知会摘要 |
| 需求台账条目 | `.document/plan/STATUS.md` | 按 `progress-tracker` 登记，状态 `开发中` |
| 重大架构决策（L3 / 不可逆变更） | `.document/adr/adr-{NNN}-{slug}.md` | ADR 格式：背景 / 选项与权衡 / 决定 / 后果 |
| 开发中的需求变更与中途决策 | 同上对应文档 | **当场更新**，并在 P12 报告「需求变动」维度记录 |

落档完成后告知用户："{文档类型}已落档：{路径}"。

> 这一步解决的问题：每次迭代、需求确认、方案设计都与开发者做了决策，但若不形成文档，
> 决策依据无法追溯、新会话无法继承、并行开发互相不可见。

## 开发前检查清单

每个计划必须包含以下检查清单（按技术栈/场景/风险选取），是进入编码阶段的**前置门禁**。

### 通用（所有场景）

```
- [ ] 技术栈已确认：前端 / 后端 / 前后端联动
- [ ] 场景类型已确认：A / B / C；风险等级已确认：LOW / HIGH
- [ ] 已查 memory（相关约束）与能力登记册（可复用清单）
- [ ] 计划已落档 + 台账已登记；砍掉 / 推迟的功能点已落 `plan/backlog-*.md`
- [ ] 联动需求：「契约」章节已冻结并经确认（纯单端写"不涉及"）
```

### 后端通用

```
- [ ] 涉及业务域已确认（新建 / 已有）；层归属已确认（domain / integration / interfaces / support）
- [ ] 接口类型已确认（api / sdk / grpc）；CommonResult/CommonPage 包装结构已确认
```

### 后端场景 B/C 附加

```
- [ ] 已读取同业务域现有代码，确认代码风格
- [ ] 已确认现有 Service 方法命名（get/getXxxList/statistics/add/update/remove）
- [ ] 已确认现有 Controller 路径结构（/v{n}/{平台}/{业务}）
- [ ] 已确认 Operate / Query 是否继承 CommonOperate / CommonQuery<T>
```

### 后端场景 C 附加

```
- [ ] 影响面分析已完成（受影响的 Service、Controller、Mapper、QueryChain）+ 调用链已列出
- [ ] 回滚方案已制定；改动范围已约束（外科手术式，只改必要的）
```

### 后端跨业务域写操作附加

```
- [ ] 跨业务域写操作放在 integration/business/{业务}/Flow 中（禁止 domain Service 处理）
- [ ] Flow 通过 Service 操作数据库（禁止直接操作 Mapper）；必要时已使用 @Transactional
```

### 后端关键风险附加

```
- [ ] 权限/鉴权：已确认 SessionContext / SecurityToken 使用方式
- [ ] 缓存：@CacheRead/@CachePut/@CacheEvict 注解和 key 命名已确认
- [ ] 分布式锁：@DistributedLock 的 key、prefix、waitTime、leaseTime 已确认
- [ ] DDL：TableDef 已按 `tabledef` skill 同步维护方案确认
- [ ] proto：字段编号未复用（删除需 reserved）；敏感字段已加 @Encryption
- [ ] 支付/资金：金额 BigDecimal、业务单号唯一索引 + 幂等、@DistributedLock(transactional)、行锁、同事务流水（`financial` skill）
- [ ] 对外接口 / SDK / proto 变更：对接文档同一次提交更新
- [ ] 含敏感 payload 的接口：加入 yzj.logger.ignore-request-url / ignore-response-url
```

### 前端通用

```
- [ ] 涉及页面/模块已确认；组件方案已确认（新建 / 复用 / 改造）
- [ ] 已确认可参考的 frontend skill（view-conventions / i18n-automation 等）
```

### 前端场景 B/C 附加

```
- [ ] 已读取同模块现有页面代码，确认结构与风格
- [ ] 已确认组件命名规范和拆分粒度；路由结构和菜单配置方式
- [ ] 已确认数据请求方式与后端接口对接的数据结构
```

### 前端场景 C 附加

```
- [ ] 影响面分析已完成（受影响的页面、组件、store、路由）+ 组件引用链已列出
- [ ] 改动范围已约束；公共组件修改已评估对其他页面的影响
```

### 前端关键风险附加

```
- [ ] 全局状态：store 结构和影响范围已确认
- [ ] 路由/权限：路由守卫逻辑和菜单权限配置已确认
- [ ] 公共组件：被引用位置和使用方式已确认
- [ ] 第三方库：版本、bundle 体积、按需加载已确认
- [ ] 国际化：i18n key 命名规范和 locale 文件更新已确认
- [ ] 全局样式：CSS 变量/主题变量影响范围已确认
```

## Review 门禁机制

### 执行前置条件（硬性门禁）

不论把握度多高，以下条件**全部满足**才能写业务代码：

| 门禁 | L1 | L2 | L3 |
|------|:--:|:--:|:--:|
| 技术栈 / 场景 / 风险已确认 | ✅ | ✅ | ✅ |
| **需求/调整文档已输出 + 用户复核对齐通过** | — | — | ✅ |
| **技术设计文档已输出 + 明确的文档评审确认 交开发者技术审核 + 二次评估通过** | — | ✅ | ✅ |
| 简化计划已输出 + 用户确认 | ✅ | — | — |
| 开发前检查清单已填写；**对应文档已落档 + 台账已登记** | ✅ | ✅ | ✅ |
| 至少 1 轮对话确认方案方向 | — | ✅ | ✅ |
| 至少 2 轮对话覆盖核心维度 | — | — | ✅ |
| 系统影响评估 + ADR 包含在技术设计文档中 | — | — | ✅ |
| 关键风险附加检查项全部通过（仅 HIGH RISK） | ✅ | ✅ | ✅ |
| 视觉交互 DEMO 已确认（仅当用户要求视觉方案 / 全新无参照视觉） | ◯ | ◯ | ◯ |
| 「契约」章节已冻结并经开发者确认（仅前后端联动 / 对外接口） | ◯ | ◯ | ◯ |

> ◯ = 按需触发。**L3 顺序固定**：需求门禁（用户复核）在前 → 技术门禁（开发者技术审核 + 二次评估）在后，不可颠倒。

> **"我觉得方案很简单/很有把握"不是跳过对齐的理由。** 对齐的价值不仅是方案正确性，更是让用户对即将发生的变更有预期、有控制权。

### 什么算"评审通过"（用户复核 / 开发者技术审核同此标准）

- 对当前计划明确批准 / 明确说"可以"/"没问题"/"按这个来"/"技术上没问题" → ✅
- 提出修改意见 → 修改对应文档后重新等待确认
- 没有回应、不确定 → **不算通过，主动询问**
- L3 需求门禁与技术门禁**分别确认**：用户对需求文档说 OK ≠ 开发者对技术设计说 OK

### 自我降级判断

认为任务复杂度低于用户标注级别时，**不要自行降级**：说明判断和理由，等待用户确认后才调整。

## 语义识别指南

| 用户表达 | 可能的真实意图 | 应对策略 |
|----------|----------------|----------|
| "这块不太对" | Bug / 重构 / 设计分歧 | 先问"是行为问题还是代码问题？" |
| "加个 X 功能" | 可能有更简单的路径 | 先问"X 要解决什么问题？" |
| "优化一下" | 性能 / 可读性 / 架构 | 先问"优化目标？当前问题在哪？" |
| "参考 Y 做一个类似的" | 复用 or 定制 | 先读 Y，评估复用程度，再提方案 |
| "帮我改一下这个逻辑" | 范围可能远超"一下" | 先读代码评估影响，再确认边界 |
| "直接做吧" / "不用问了" | 希望跳过对齐 | 降级到最简确认，仍出计划后执行 |
| "加个页面" / "做个弹窗" | 缺交互细节 | 先问"展示什么数据？主要交互？" |
| "样式不对" | 布局/响应式/主题各不同 | 先问"具体哪里？能指出元素吗？" |

**提问原则**：保持对话感而非问卷感（每轮 1-2 个问题）；说出你的理解让用户纠正；合理推断不需要问；效率优先，信息足够不为流程而追问。
