# 开发成果总结（dev-output）

> 每次开发 session 收尾时，将工作成果以结构化文档输出，供团队核实需求进度和业务变更。
> 报告文件名与 `STATUS.md` 台账条目同名，形成「台账 → 报告」的追溯链。

---

## 一、输出路径与命名

**目录**：`{project_root}/.document/developer/output/`

**文件名**：`{yyyy-MM-dd}_{stage}_{business}.md`（= 台账条目名）

| 占位符 | 说明 | 示例 |
|--------|------|------|
| `yyyy-MM-dd` | 需求启动日期（与台账一致） | `2026-06-06` |
| `stage` | 迭代阶段（从 `00-plan-overview.md` 读取） | `MVP` / `p1` / `P4` |
| `business` | 业务域英文短名（kebab-case） | `workitem-crud` / `ai-doc-auto-index` |

同一天同一业务多次输出时追加序号：`..._-2.md`。

---

## 二、内容模板

按以下 7 个维度组织。**仅写有实质内容的维度**，无内容的标注「无」或省略整节。

```markdown
# {业务名称} — 开发成果总结

> 日期：{yyyy-MM-dd} | 阶段：{stage} | 业务域：{business} | 变更级别：ARCH / NORMAL

---

## 1. 业务背景

**需求来源**：计划文档驱动（引用 `.document/plan/{xx}.md` 任务编号）/ 开发者临时提出（简述原始描述）
**业务目标**：一句话说明本次要达成的业务效果。

## 2. 需求变动

> 无变化写「无变动」。

| 变动项 | 原始需求 | 最终实现 | 变动原因 |

## 3. 开发者对话总结

- **开发者提出的关键决策**：{决策及理由}
- **Review 反馈摘要**：{P6 反馈要点；NORMAL 级写"知会确认通过"}
- **测试反馈摘要**：{P7 发现的问题及修复}
- **架构/设计讨论**：{如有}

## 4. UI / 视觉改动

> 无前端或无视觉变更写「无 UI 改动」。

- **新增页面/组件** / **交互变更** / **样式调整**

## 5. 前端开发内容

> 无前端开发写「无前端改动」。

### 新增/修改文件清单
| 文件路径 | 操作 | 说明 |

### 技术要点
- {关键实现逻辑、组件设计、状态管理等}

## 6. 后端开发内容

> 无后端开发写「无后端改动」。

### 新增/修改文件清单
| 文件路径 | 操作 | 说明 |

### 接口变更
| 方法 | 路径 | 说明 |

### 数据库变更
| 表名 | 变更类型 | 说明 |

### 技术要点
- {关键实现逻辑、设计决策、踩坑记录等}

## 7. 总结

**完成情况**：{完成了哪些任务，对应 plan 文档哪些条目}
**测试结论**：{testcases 文档链接 + P5/P7 结果（N/M 通过；手测 or AI E2E）+ 未覆盖项}
**回溯扫描**：{similar-issue-sweep 结论：扫描 N 处 / 修复 M 处 / 无同类}
**遗留事项**：{未完成或需跟进的事项；列入台账或 plan 的写明位置；本次砍掉 / 推迟的功能点给出 plan/backlog-*.md 链接}
**关联沉淀**：{写入的 memory 文件名 / 登记的能力 / 反哺项}
```

---

## 三、执行流程

1. **收集信息**：P1 开发范围与变更级别 → 业务背景；P3 代码变更 → 文件清单（`git diff --name-only` 辅助核对，不遗漏）；P4 回溯扫描结论；P6-P8 开发者交互 → 对话总结、需求变动；P9 进度 → 完成情况；P10 沉淀 → 关联沉淀
2. **确定文件名**：取台账条目名（P1 已登记）
3. **填写模板**：写事实不写废话；文件清单完整；接口变更准确（method + path）；数据库变更列全；对话总结提炼关键决策而非复制聊天记录
4. **输出文件** 并在台账「已完成」区附上报告链接；已完成区超 20 条 → 按 `progress-tracker`「台账容量治理」归档溢出条目
5. **告知开发者**：

```
## P12 开发成果已输出
📄 `.document/developer/output/{filename}.md`
摘要：业务域 {business} / 完成 {N} 项 / 前端 {M} 文件 / 后端 {K} 文件 / 需求变动 {有无} / 沉淀 {数量}
```

---

## 四、注意事项

- 每次 dev-session 都应产出一份总结；轻量任务至少包含维度 1、6/7
- 总结文档随代码提交入库（P11 commit 包含或追加 commit）
- 一个 session 跨多业务域时，按主业务域命名，文档内说明其他涉及域
- 不写入敏感信息（密钥、密码等）
