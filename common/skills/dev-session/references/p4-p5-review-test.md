# dev-session · P4–P5：AI Review → AI 自测

> 门禁：P4 不可跳过（规则 4），reviewer 全文加载、逐维度结论齐备才可进 P5；P5 先产测试用例文档再自测。硬门禁常驻摘要见 `red-lines.md`，主文件 `SKILL.md`。

## P4：AI Review

**执行者**：AI | **关联 skill**：backend `reviewer`、frontend `reviewer`、`api-contract-checker`、`similar-issue-sweep`

**加载方式**：reviewer 是兜底硬门禁，进入 P4 必须**全文加载**（不按维度抽读）。有子代理 / 多会话能力的宿主（Claude Code：`Agent`；Codex：子代理）优先在**新的子代理**中执行——只加载 reviewer 全文 + 本次 diff + 恢复卡，结论写回 `design/{slug}-review.md`，主会话只读报告，避免主会话上下文峰值；无子代理能力时主会话执行，P4 前先完成 P3 收尾与恢复卡更新。

1. **后端**：按 backend `reviewer` 的**七步硬流程**执行（含进入前的 echo 协议、强制 Grep 扫描、漏检史核对），逐维度 × 逐文件全覆盖，**禁止选择性抽查**
   - 后端仓与基线不同栈、没有自身 reviewer 时：框架专属规则（Controller 形态、TableDef、Operate 继承等）不套用，以该仓现有写法为准；但**代码格式与注释排版**仍按 backend `reviewer` 第三、五节与 Step 2 排版四项审——"以现有风格为准"不是跳过排版审查的理由。存量文件只审本次改动行，新增文件全文审
2. **前端**：按 frontend `reviewer` 的七步硬流程执行，同样全覆盖
3. **跨端**：涉及接口的变更运行 `api-contract-checker`
4. **同类问题回溯**：本次变更若属于修复/纠正类，按 `similar-issue-sweep` 扫描全库同类问题（规则 2）
5. 发现问题 → **自行修复** → 重跑对应扫描验证无回归，不留给开发者

**放行门禁**：reviewer 报告每个维度都必须是「✅ + 依据 / ❌ N 处 / 未检查（原因）/ N/A（原因）」之一；存在「未检查」、未处理的 review-scan HIT 或未判定的 CANDIDATE 时 P4 未完成，不得进 P5。「已 Read reviewer 全文」只证明读过规则，不能当审查结论；审查矩阵不得按文件路径或类型生成。

**出口**：审查报告（逐维度结论）+ 回溯扫描结果，所有可自修问题已修复；回执 `[P4 ✅ | 依据 design/{slug}-review.md 全维度 ✅、回溯 N 处 | 下一步 P5]`

## P5：AI 自测

**执行者**：AI | **关联产物**：测试用例文档（自测前硬门禁）

### 第 0 步：输出测试用例文档（自测开始前，前后端通用，不可跳过）

自测**开始前**先产出测试用例 Markdown，落档 `design/{yyyy-MM-dd}_{slug}-testcases.md`（与技术设计文档同 slug；轻量任务见 `references/flow-control.md`「轻量任务简化」）——让开发者在 P6 能确认"这次要测什么、要回归什么"，P7 据此验收 / E2E。文档骨架见 `templates/testcases.md`。

**用例拟定原则**（先于模板）：

1. **按实际场景拟定，不按骨架铺满**：TC-1～TC-4 每类只写本次改动真实可达的场景；有技术设计 / 需求文档时，用例从其「验收标准」「契约」逐条展开并标注来源条目；文档没有的场景不凭空补。某一类确实不适用写 `N/A（原因）`，不编用例凑数。
2. **回归按影响面划定，不过度回归**：TC-5 的来源只认 P4 影响面分析与 `similar-issue-sweep` 扫描结果（调用方、共用组件 / Service、同表读写、同契约两端）；不在影响面内的既有功能不列。每条回归标注"为什么会被波及"，说不出理由的不列。
3. **拿不准先对齐一次**：对用例是否正确、场景是否遗漏、回归范围是否过宽 / 过窄没有把握时，**在执行自测前**把用例摘要（各类条数 + 存疑项）给开发者确认一次，按反馈修订后再跑；不在存疑状态下直接执行，也不把疑问留到 P6 才暴露。对齐中的纠正按规则 1 沉淀。

- **TC-5 回归范围不可省略**：改了 A 必须写明要回归哪些既有功能——这是开发者最关心、也最容易被跳过的一栏
- 每条 TC 标注**执行方式**（AI 可测 / 需真机 / 需开发者）；P5 只执行「AI 可测」项，其余留给 P7 并在出口明示

### 自测执行（按用例逐条执行，结果回填「执行记录」）

**后端**：执行项目入口文件定义的编译/测试命令（如 `mvn compile -pl {module} -am -q`），失败 → 修复 → 重试直到通过；「AI 可测」的用例优先落成单元测试（backend `testing` skill：命名、模板、金融 / 权限必测场景），其余可运行验证的用例（起服务调接口）逐条执行核对。

**前端 —— 两轮自测机制**

优先使用宿主可用的浏览器 / 预览能力（如 Claude Code 内置浏览器与 preview 工具）验证渲染、交互、控制台与网络；无可用工具时退化为 `build + 类型检查 + 手动验证指引`，并如实列出未验证的交互。

**第一轮（MOCK 视觉/交互验证）**：页面渲染、console 无报错、核心交互、响应式断点、设计系统 token 抽样、关键页面截图归档（作为 P6 材料）。

**第二轮（接口对接后功能验收）**：重跑第一轮 + 网络请求校验（URL/Header/Payload 对齐后端 VO/Operate）+ 数据流验证（创建 `Long`/更新删除 `Boolean`/分页字段解析）+ 异常路径（错误码/超时的 toast 与 loading 态）+ 权限/多租户隔离（如适用）；接口对接暴露的新场景**同步更新用例文档**（新增/修正 TC）。

**出口**：测试用例文档已落档且每条可追溯到场景 / 文档条目 / 影响面依据、「AI 可测」用例全部通过且结果已回填；编译/构建通过；「需真机 / 需开发者」用例已列为 P7 待办；台账迁 `待Review`；回执 `[P5 ✅ | 用例 N/M 通过，待 P7 K 条 | 下一步 P6]`
