# dev-session · P4–P5：AI Review → 测试范围与用例

> 门禁：P4 不可跳过（规则 4），reviewer 全文加载、逐维度结论齐备才可进 P5；P5 只确认测试 / 回归范围并产出用例文档（单元测试在 P3），不做用例验收 / E2E（归 P7）。硬门禁常驻摘要见 `red-lines.md`，主文件 `SKILL.md`。

## P4：AI Review

**执行者**：AI | **关联 skill**：backend `reviewer`、frontend `reviewer`、`api-contract-checker`、`similar-issue-sweep`

**加载方式**：reviewer 是兜底硬门禁，进入 P4 必须**全文加载**（不按维度抽读）。有子代理 / 多会话能力的宿主（Claude Code：`Agent`；其他宿主：确认其子代理 / 多会话能力可用后再用，未核实前按无子代理处理）优先在**新的子代理**中执行——只加载 reviewer 全文 + 本次 diff + 恢复卡，结论写回 review 报告，主会话只读报告，避免主会话上下文峰值；无子代理能力时主会话执行，P4 前先完成 P3 收尾与恢复卡更新。

**报告落档（任何级别）**：`design/{yyyy-MM-dd}_{slug}-review.md`（与技术设计文档同 slug）。ARCH 按 reviewer「审查报告格式」全量、多轮在同一份追加；NORMAL 可精简为逐维度结论表 + Step 2 扫描输出，但必须落盘——它是「进度判定」表的磁盘信号，也是 P6 知会的依据。

1. **后端**：按 backend `reviewer` 的**七步硬流程**执行（含进入前的 echo 协议、强制 Grep 扫描、漏检史核对），逐维度 × 逐文件全覆盖，**禁止选择性抽查**
   - 后端仓与基线不同栈、没有自身 reviewer 时：框架专属规则（Controller 形态、TableDef、Operate 继承等）不套用，以该仓现有写法为准；但**代码格式与注释排版**仍按 backend `reviewer` 第三、五节与 Step 2 排版四项审——"以现有风格为准"不是跳过排版审查的理由。存量文件只审本次改动行，新增文件全文审
2. **前端**：按 frontend `reviewer` 的七步硬流程执行，同样全覆盖
3. **跨端**：涉及接口的变更运行 `api-contract-checker`
4. **同类问题回溯**：本次变更若属于修复/纠正类，按 `similar-issue-sweep` 扫描全库同类问题（规则 2）
5. 发现问题 → **自行修复** → 重跑对应扫描验证无回归，不留给开发者；修复动到业务代码或测试代码时**重跑单元测试**，以最新结果为准（P5 不再重跑）

**放行门禁**：reviewer 报告每个维度都必须是「✅ + 依据 / ❌ N 处 / 未检查（原因）/ N/A（原因）」之一；存在「未检查」、未处理的 review-scan HIT 或未判定的 CANDIDATE 时 P4 未完成，不得进 P5。「已 Read reviewer 全文」只证明读过规则，不能当审查结论；审查矩阵不得按文件路径或类型生成。

**出口**：审查报告（逐维度结论）已落档 + 回溯扫描结果，所有可自修问题已修复；回执 `[P4 ✅ | 依据 design/{yyyy-MM-dd}_{slug}-review.md 全维度 ✅、回溯 N 处 | 下一步 P5]`

## P5：测试范围与用例

**执行者**：AI | **关联产物**：测试用例文档

> 定位：P5 **只确认测试范围与回归范围、产出用例**；单元测试已在 P3 写完并通过，这里不重写、不重跑；不做用例验收、E2E、浏览器 / 预览验证——用例验收统一在 P7（开发者手测或委托 AI E2E），P7 不跑单元测试，三阶段不重叠。

### 第 1 步：确认测试范围与回归范围

- **测试范围**（TC-1～TC-4）：有技术设计 / 需求文档时，从其「验收标准」「契约」逐条展开并标注来源条目；只写本次改动真实可达的场景，文档没有的场景不凭空补
- **回归范围**（TC-5）：来源只认 P4 影响面分析与 `similar-issue-sweep` 扫描结果（调用方、共用组件 / Service、同表读写、同契约两端）；不在影响面内的既有功能不列，每条标注"为什么会被波及"，说不出理由的不列

### 第 2 步：产出测试用例文档（前后端通用，不可跳过）

落档 `design/{yyyy-MM-dd}_{slug}-testcases.md`（与技术设计文档同 slug；轻量任务见主文件阶段路由表下「细则」所指流程控制细则的「轻量任务简化」）——让开发者在 P6 确认"这次要测什么、要回归什么"，P7 据此验收 / E2E。文档骨架见 `templates/testcases.md`。

**用例拟定原则**：

1. **按实际场景拟定，不按骨架铺满**：某一类确实不适用写 `N/A（原因）`，不编用例凑数。
2. **回归按影响面划定，不过度回归**：同第 1 步回归范围的来源约束。
3. **拿不准先对齐一次**：对用例是否正确、场景是否遗漏、回归范围是否过宽 / 过窄没有把握时，把用例摘要（各类条数 + 存疑项）给开发者确认一次，按反馈修订后再出 P5；不把疑问留到 P6 才暴露。对齐中的纠正按规则 1 沉淀。

- **TC-5 回归范围不可省略**：改了 A 必须写明要回归哪些既有功能——这是开发者最关心、也最容易被跳过的一栏
- 每条 TC 标注**验收方式**（AI E2E 可测 / 需真机 / 需开发者），供 P7 选择手测或委托 AI E2E；「执行记录」只留 P7 列，P5 不回填执行结果
- 「单元测试」表登记 P3 已写的测试（测试类 # 方法 ↔ 覆盖的 TC ↔ 最近一次结果，含 P4 自修后的重跑），让 P6 / P7 看到哪些 TC 已有单测兜底；P3 记了 N/A 的照录原因

**前端两轮**：后端接口未就绪走双轮时，第一轮（MOCK）用例覆盖页面渲染、核心交互、响应式断点等视觉 / 交互场景；对接接口后的第二轮补齐网络请求（URL/Header/Payload 对齐后端 VO/Operate）、数据流（创建 `Long`/更新删除 `Boolean`/分页字段解析）、异常路径（错误码/超时的 toast 与 loading 态）、权限 / 多租户隔离（如适用）等用例，**同步更新用例文档**（新增 / 修正 TC）。

**构建底线**：出口前编译 / 构建（含类型检查）须通过（命令按项目入口文件，如 `mvn compile -pl {module} -am -q`、`npx vite build`）。

**出口**：测试用例文档已落档，每条可追溯到场景 / 文档条目 / 影响面依据，TC-5 回归范围已写明，存疑项已与开发者对齐；单元测试表已登记；编译 / 构建通过；台账迁 `待Review`；回执 `[P5 ✅ | 用例 N 条（回归 K 条），验收待 P7 | 下一步 P6]`
