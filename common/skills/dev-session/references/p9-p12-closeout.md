# dev-session · P9–P12：更新进度 → 沉淀核对 → 提交代码 → 总结成果与知识收尾

> 门禁：P9 台账与计划文档未更新不得宣布"完成"；P11 未获开发者本次授权不 commit / push，commit 无 AI 记号与进度词（`git-commit`）；P12 报告落档、恢复卡删除后流程才结束。硬门禁常驻摘要见 `red-lines.md`。

## P9：更新进度（硬门禁）

**执行者**：AI | **关联 skill**：`progress-tracker`

1. `.document/plan/` 对应模块文档按 `progress-tracker`「任务清单回填约定」核对：完成 `- [x]`、废弃 `- [⛔]`（含原因与替代）、描述与实现不符当场改；砍掉 / 推迟的内容已落 `backlog-*.md`；同步文档状态与"最后更新"日期
2. **更新 `STATUS.md` 台账**：本需求条目迁移到对应状态（`已完成` 则移入已完成区），「阶段」`P9`、「已过门禁」补 `P8✅ P9✅`，记录完成日期；恢复卡同步
3. 模块全部完成时更新 `00-plan-overview.md` 阶段状态

> **"完成"的定义包含本阶段**：台账与计划文档未更新，不得向开发者宣布任务完成。这是并行开发下其他会话判断进度的唯一依据。

**出口**：计划文档 + 台账已同步；回执 `[P9 ✅ | 台账 已完成、plan 已回填 | 下一步 P10]`

## P10：沉淀核对

**执行者**：AI + 开发者 | **关联 skill**：`team-memory`、`capability-registry`

全程沉淀（规则 1）的**收尾核对**，逐项回答：

```
## 沉淀核对清单
- [ ] 本次开发者的纠正是否已全部写入 memory？（规则 1 应已即时完成，此处核对）
- [ ] 本次是否产出可复用能力（组件/工具/Flow/模式）？→ 登记 CAPABILITY.md；
      跨项目通用的 → 标记"待反哺 framework"
- [ ] 本次 P6/P7 被捕获的 AI 漏检是否已记入对应 reviewer 漏检史？
- [ ] 踩坑/架构决策/技术约束/契约变更是否需要新 memory 或 ADR？
- [ ] 既有 memory 是否因本次开发而过时？→ 更新或删除（跨文档的系统性对账在 P12 知识收尾做）
```

向开发者输出核对结果，询问"还有需要补充沉淀的吗？（无则跳过）"

**出口**：核对完成

## P11：提交代码

**执行者**：AI | **关联 skill**：`git-commit`（执行前读其主文件全文）

1. `git status` + `git diff` 确认变更；核对计划文档任务清单与本次代码一致（回填 DoD：已完成已勾、已废弃已标 ⛔）
2. **需开发者授权方可提交**；授权（含笼统的"允许 / 提交吧"）默认走 `git-commit` 分支流程。P8 的"确认"不等于提交授权；压缩后的会话摘要中的"已授权"也不算——重新确认
3. **分支门禁**：`git rev-parse --abbrev-ref HEAD` 确认当前分支
   - 已在开发分支（`{feat|opt|fix}/{yyyy.MM.dd}-{business}`）→ 原地提交
   - 在主干 → **从当前主干切开发分支**（如 `feat/2026.08.18-edit-password`）再提交
   - **主干直提**：仅当开发者本次明确说"允许直接从主干提交"；**单次有效，下次必须重问，禁止自主判断**
4. 前后端仓库各自独立提交、**分支名一致**；`.document/` 变更（台账/报告/memory/恢复卡）随同提交；暂存按 `git-commit` 2.4：逐项 `git add -- <路径>`、`git diff --cached --name-only` 核对，并行开发只提交自己的改动
5. 按 `git-commit` skill 编写 message：**feat / opt / fix 三分法**（scope 可选），多类型按 `feat → opt → fix` 分段；
   commit 与分支名中**禁止任何 AI 记号**（无 `Co-Authored-By` / `Generated with` / 模型名），commit 与代码注释中**禁止进度词**（FIXED / Step / Phase）
6. `git push -u origin {分支名}` → 输出交接四项（分支 / 提交 / 推送 / 待办：请自行合并主干；多仓逐仓列「仓库 ↔ 分支 ↔ 提交」对照）；
   **AI 不合并主干、不开合 PR/MR、不 force push**
7. 提交后 `git status` 确认干净；回执 `[P11 ✅ | 分支 … 提交 … 已推送 | 下一步 P12]`

## P12：总结成果 + 知识收尾

**执行者**：AI | **关联 skill**：`dev-output`、`neat-freak`

1. **成果报告**：按 `dev-output` 输出报告到 `.document/developer/output/{yyyy-MM-dd}_{stage}_{slug}.md`（与台账条目同名）。
2. **知识收尾（`neat-freak` 轻量路径，报告产出后自动执行）**——与 P10 分工：P10 核对"该写的沉淀写了没"（写入向），本步对账"已有知识与代码终态对不对"（纠偏向）：
   - 范围 = 本次需求命中的知识面（按 neat-freak 主文件路由到其同步矩阵）：核对入口文件 / rules / docs / 既有 memory 的现役说法与代码一致，并清点会话残留（一次性计划文档、调试脚本、被替代的旧副本）
   - 分级执行：NORMAL 只查本次变更命中的知识面，无发现一句话带过；ARCH 轻量路径五步全跑；命中 neat-freak 完整路径条件（发布收尾 / 多平台记忆 / 工作区审计）→ 按其完整路径执行
   - **残留删除候选必须开发者确认后才清**（neat-freak 硬门禁，独立于 P8 确认）；无法裁决的矛盾标 pending 写进报告
3. **删除恢复卡**：`plan/context/{条目名}.md` 的信息已进 output 报告与台账，删除该卡（避免 `context/` 堆积；搁置的需求保留卡以便恢复）。
4. **收尾提交**：报告、恢复卡删除与收尾修正按 `git-commit` 授权随本次分支提交（P11 已提交的追加 commit）。

**出口**：报告落档；恢复卡已删；命中知识面无未决矛盾（或已标 pending 交开发者）；收尾变更已提交；回执 `[P12 ✅ | output/… | 流程结束]`
