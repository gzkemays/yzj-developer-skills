# dev-session · P1–P3：分析需求 → 加载沉淀 → 开发

> 门禁：P1 出口须完成台账登记 + 恢复卡；P3 编码前文档评审门禁（L2 / L3）未过不写业务代码；全程规则与分级见主文件 `SKILL.md`，硬门禁常驻摘要见 `red-lines.md`。

## P1：分析需求

**执行者**：AI | **关联 skill**：`iteration-planner`、`progress-tracker`

1. 读取 `.document/plan/STATUS.md` 台账：当前**进行中**的需求有哪些（含其他人/其他会话并行项）、本任务是否已在台账中
2. 读取 `.document/plan/00-plan-overview.md` 定位当前迭代阶段；读取用户指定的模块文档，解析未完成任务（`- [⛔]` 已废弃项不算未完成）；扫 `plan/backlog-*.md` 中相关主题，判断是否本次顺带立项
3. 若用户未指定任务，列出当前阶段未完成模块供选择
4. **并行冲突检查**：若本任务与台账中其他进行中需求涉及相同模块/文件，明确提示开发者潜在冲突
5. 判定变更级别（ARCH / NORMAL，判定标准见主文件「变更分级」），连同开发范围一句话向开发者确认
6. 在台账登记/更新本需求条目为 `开发中`（命名 `{yyyy-MM-dd}_{stage}_{slug}`，与 output 报告同名），「阶段」填 `P1`
7. **建立恢复卡** `.document/plan/context/{条目名}.md`（模板见 `templates/.document/plan/context/README.md`，项目内为 `plan/context/README.md`）：需求一句话、分级、当前阶段、下一步、工作位置（分支 / worktree / 涉及仓）、需重读清单；**不写任何授权状态**。续作已有条目 → 读卡而不是重建
8. 输出阶段回执 `[P1 ✅ | 范围 … | 分级 … | 下一步 P2]`

**出口**：开发范围 + 变更级别已确认，台账已登记，恢复卡已建立

## P2：加载沉淀

**执行者**：AI | **关联 skill**：`team-memory`、`capability-registry`

1. 读取 `.document/developer/memory/MEMORY.md`，按任务关键词定位相关 memory 并**读取全文**（feedback 类强约束必读）
2. 读取 `.document/developer/capability/CAPABILITY.md` 能力登记册：本次涉及的功能是否已有**可复用的组件 / 工具 / 业务流程 / 既有接口**——有则优先复用，禁止重复造轮子
3. 检查 `.document/adr/` 是否有相关架构决策
4. 读取个人 memory（Claude Code：`~/.claude/projects/` 下；其他宿主：用户已配置并授权的位置，未配置则跳过）
5. 向开发者一句话总结：命中的关键约束 + 可复用能力清单（如有）

**出口**：相关沉淀与可复用能力已加载并告知开发者

## P3：开发需求

**执行者**：AI（架构决策暂停等待开发者）

### 文档产出与评审门禁（编码前，按 `pre-dev-alignment`）

执行 `pre-dev-alignment`（技术栈/场景/风险判断 + 任务分级 + 结构化对话），再按任务级别走**编码前文档产出与评审门禁**——**门禁未过不写业务代码**：

| 级别 | 编码前产出 | 门禁顺序 |
|------|------------|----------|
| **L1** | 简化计划 | 用户确认方案 → 编码 |
| **L2** | 技术设计文档（`design/`） | **开发者技术审核 + 二次评估** → 编码 |
| **L3** | 需求/调整文档（`plan/`）→ 技术设计文档（`design/`） | **① 用户复核需求/调整文档**（确保需求最终对齐）→ **② 开发者技术审核 + 二次评估** → 编码 |

- **二次评估**：开发者基于技术设计文档，对方案合理性 / 工作量 / 风险 / 影响面在需求初评之上再确认一次——这是**编码前对技术设计**的审核，区别于 P6 **编码后对代码**的 Review。
- **视觉交互 DEMO（按需）**：用户要求视觉方案 / 全新无参照视觉时，技术设计阶段附带产出 `design/{slug}-demo.html` 或用前端既有组件搭 DEMO；定稿后由 AI 判断是否抽为复用组件并登记 `CAPABILITY.md`（详见 `pre-dev-alignment`「视觉交互 DEMO」）。
- **对齐结论落档**：每道门禁通过后**立即**按 `pre-dev-alignment` 落档规则写入对应目录（需求文档→`plan/`、技术设计文档→`design/`、重大架构决策→`adr/`）——口头对齐不落档 = 未对齐。

### 后端路径

- 按 `yzj-dev-workflow` 流程，编码前过其门禁清单，过程中按需引用 backend 子 skill
- 工作目录：后端仓库（项目入口文件定义）

### 前端路径

- 按 frontend 的 `view-conventions` 等 skill 编码，遵循项目入口规则的设计系统约定
- 工作目录：前端仓库（项目入口文件定义）

**前端两轮开发机制**（接口未就绪时）：
- **后端接口未就绪** → 双轮：第一轮基于 MOCK 实现视觉/交互层（在 service 层用环境开关条件分支返回 mock，要求"删除/翻转一处即可切换真实接口"，不引入难剥离的 mock 框架）；P5/P6 第一轮通过后回到 P3 对接接口，再走 P5/P6 第二轮
- **后端接口已就绪** → 单轮：直接对接，P5/P6 合并视觉与接口验证

> 与编码前的**视觉交互 DEMO** 区分：DEMO 在 P3 文档阶段定视觉 / 交互**方向**；MOCK 轮是**真实页面实现**。DEMO 已抽成复用组件的，MOCK 轮直接复用，不重复造。

### 全栈路径

1. 接口契约已在技术设计文档「契约」章节冻结（`pre-dev-alignment`）；开发中契约要变 → **先改设计文档再改两端实现**，禁止先改实现后补文档
2. 先后端 → 后前端（后端完成不暂停，直接进前端）；前端按「前端对接映射」表逐条对接并回填两端状态
3. 运行 `api-contract-checker` 以契约章节为对照检查前后端一致性
4. P6-P8 在前后端全部完成后统一触发

**出口**：代码实现完成；回执 `[P3 ✅ | 对齐 design/… | 下一步 P4]`
