# dev-session · P6–P8：开发者 Review → 开发者 / AI E2E 测试 → 开发者确认

> 门禁：P6 开发者未回复不得进 P7 / P8；P7 不通过必须修复后重走 P4 → P5 → P6 → P7；P8 须开发者明确说"确认"才执行 P9–P12（验收确认，不是 Git 提交授权，P11 另取）。参与深度按主文件「变更分级」（ARCH / NORMAL）。硬门禁常驻摘要见 `red-lines.md`。

## P6：开发者 Review

**执行者**：开发者 | **AI 暂停等待**

### ARCH 架构级 —— 深度评审

AI 输出完整 Review 材料（骨架见 `templates/review-materials.md`「ARCH 架构级」）：变更摘要 / 架构影响 / AI Review 报告 / P5 自测结果 / 测试用例链接 / 需要决策，末行请开发者逐项审阅——通过 → 进入 P7；有问题 → 描述，AI 修复后重走 P4。

前端任务保持两轮（视觉 Review → 功能 Review）：开发者明确说"视觉通过"才对接接口，明确说"功能通过"才进 P7。

### NORMAL 常规级 —— 知会式确认

AI 输出精简摘要（10 行内，骨架见 `templates/review-materials.md`「NORMAL 常规级」）：变更 / 自审 / 自测 + 用例 / 风险，末行"过目后任意回复即视为确认（如需深度 Review 请说"升级 ARCH"）"。

开发者**任意明确回复**（"OK"/"继续"/"知道了"）即过；超出摘要外的疑问或要求 → 升级为 ARCH 深度评审。

**门禁**：开发者未回复前不得进入 P7/P8。通过后台账迁 `待验收`，回执 `[P6 ✅ | ARCH 深评 / NORMAL 知会 | 下一步 P7]`。

---

## P7：开发者 / AI E2E 测试

**执行者**：开发者手测，或开发者委托 AI 执行 E2E | **测试依据**：P5 测试用例文档

- 可实际运行验证时进行（前端可页面操作 / 后端可起服务调接口）；无法运行验证的任务跳过 → P8
- **NORMAL 级**：开发者可回复"免测"跳过
- 进入本阶段时 AI 输出测试指引：启动方式（项目入口文件的命令）+ 用例文档路径 + 验收条件

### 方式一：开发者手测（默认）

开发者按用例文档操作验收，AI 协助调试；结果由 AI 回填用例文档「执行记录」。

### 方式二：AI E2E（开发者说「E2E 自测」/「你来 E2E」时执行）

1. **环境准备清单先行**：向开发者列出前置项并等待就绪确认——需启动的服务、账号 / Token 令牌、测试数据、真机或设备（如需）；有一项未就绪不开测
2. **按用例逐条执行**：按 P5 用例文档 TC 顺序做端对端验证（真实服务、真实接口，禁用 MOCK），逐条记录实际结果与证据（关键响应 / 截图 / console / 数据核对）
3. **结果回填与报告**：结果写回用例文档「执行记录」，输出 E2E 摘要（N/M 通过 + 失败详情 + 未覆盖项：标注「需真机 / 需开发者」的用例）
4. **AI 不得自我判定通过**：E2E 结果交开发者确认——「通过」只能由开发者说；未覆盖项由开发者决定补测或豁免

**门禁**：开发者明确说"通过"后进 P8。
**不通过（硬规则）**：AI 修复（含回溯扫描）后**必须重走 P4 → P5 → P6 → P7 完整链路**，禁止跳过 Review / 自测直接复测失败用例；失败场景在 P5 重跑时固化为新增 TC，防同一问题再漏。

## P8：开发者确认

**执行者**：开发者 | **硬门禁**

```
Review 通过 + 测试通过。确认验收通过、进入收尾（P9 进度 → P10 沉淀 → P11 提交 → P12 报告）？（确认/否）
```

开发者明确说"确认"/"通过"/"OK"后才执行 P9–P12。不通过 → 回退 P6。P11 的 Git 提交授权届时按 `git-commit` 另问一句，不在此处合并取得。
NORMAL 级在 P6 知会确认中合并完成，不再二次询问。

**出口**：回执 `[P8 ✅ | 开发者确认原话摘录 | 下一步 P9]`；该确认不等于 Git 提交授权——P11 另按 `git-commit` 取得。
