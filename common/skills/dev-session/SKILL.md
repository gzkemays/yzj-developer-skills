# 研发生命周期（dev-session）

> 所有开发任务统一走此流程。AI 自主推进 P1-P5；P9-P12 以 AI 为主，其中 P10 沉淀核对与 P12 残留清理需开发者确认、P11 提交需开发者授权；P6-P8 按变更分级决定开发者参与深度。
> 项目专有信息（仓库路径、构建命令、设计系统、契约约定）以项目根**入口文件**及其引用规则为准（Claude Code：`CLAUDE.md`；其他宿主：AGENTS.md），本 skill 只定义流程。
> **加载方式**：本文件是主文件——读完全文后，按「阶段路由表」只读**当前阶段**的子文件；不一次读完所有子文件。硬门禁常驻摘要在常驻规则 `red-lines.md`（每条带本技能章节指针，章节在主文件或路由指向的子文件内）。

## 约束卡（凌驾于任何单阶段之上）

| 规则 | 要求 | 细则 |
|------|------|------|
| **规则 1 纠正即沉淀** | 开发者任何阶段纠正 AI（否决方案 / 指出代码问题 / 提醒规范 / 推翻设计）→ 完成修正 → **立即**按 `team-memory` 写 feedback memory（开发者原话 + Why + How to apply）并更新 `MEMORY.md` 索引 → 响应中告知"已沉淀至 memory：`{文件名}`"。不推迟到 P10（P10 只核对不补救）；同一问题被纠正第二次 = 机制失效，升级为强约束并记入对应 reviewer 漏检史 | `team-memory` |
| **规则 2 修复必回溯** | 任何 bug 修复 / 违规修正 / 优化落地后按 `similar-issue-sweep` 全库扫同类并一并处理；只修被指出的一处 = 流程违规 | `similar-issue-sweep` |
| **规则 3 进度实时更新** | 状态迁移**当下**改 `STATUS.md`（状态 / 阶段 / 已过门禁）并同步本需求**恢复卡** `plan/context/{条目名}.md`，不等收尾；台账是并行开发下唯一可信进度源，恢复卡是压缩后重新定位的依据 | `progress-tracker`；下文「进度判定」 |
| **规则 4 P4 不可跳过** | 任何 P3 编码（含改一行）完成后、进 P5 前必过前/后端 reviewer 硬流程，"改动小 / 有把握"不是理由；**P6/P7 发现问题后的修复同样是编码**，修完重走 P4 → P5 再回对应门禁，禁止只复测失败用例 | `references/p4-p5-review-test.md`；`references/p6-p8-developer-gates.md`（P7 不通过）；下文「回退规则」 |

## 变更分级（P1 判定，决定 P6-P8 深度）

| 级别 | 判定标准（命中任一即是） | P6 | P7 | P8 |
|------|--------------------------|----|----|----|
| **ARCH 架构级** | 影响整体架构或框架设计；新增/调整核心数据模型；安全、权限、鉴权、资金；跨业务域流程（Flow）；对外契约变更（API 破坏性调整 / proto）；开发者标注"重要需求"；不可逆变更（数据迁移、删字段） | 深度评审：开发者逐项审阅 Review 材料 + 关键代码 | 必须执行（手测或委托 AI E2E） | 必须明确确认（验收确认，不是提交授权） |
| **NORMAL 常规级** | 常规需求开发与迭代：新增页面/接口/字段、普通 bug 修复、样式调整、文案/i18n | 知会式确认：AI 输出精简摘要，开发者**过目**后任意明确回复即过 | 自行决定：手测 / 委托 AI E2E / 免测 | 与 P6 合并的一次确认 |

**拿不准时按 ARCH 处理。** 分级结果在 P1 出口明示开发者，开发者可以改判。

> 设计意图：开发者掌控方向与架构，把注意力从逐行 review 中释放出来；AI 用更严格的自审（P4 硬流程 + 回溯扫描）换取常规变更的自主权。NORMAL 级自审漏检被开发者捕获 → 按规则 1 沉淀并记入 memory；连续漏检的同类变更自动升级 ARCH。

## 阶段路由表（按当前阶段只读对应子文件）

| 阶段 | 执行者 | 子文件（必读） | 关联 skill | 出口门禁 |
|------|--------|----------------|------------|----------|
| **P1 分析需求** | AI | `references/p1-p3-develop.md` | `iteration-planner`、`progress-tracker` | 范围 + 分级已确认；台账登记；**恢复卡已建** |
| **P2 加载沉淀** | AI | 同上 | `team-memory`、`capability-registry` | 相关 memory / 能力 / ADR 已加载并告知 |
| **P3 开发需求** | AI | 同上 | `pre-dev-alignment`、`yzj-dev-workflow` / frontend skills、`api-contract-checker` | **编码前文档评审门禁**（L2 / L3）通过且已落档；开发中契约要变**先改设计文档再改实现**；代码完成 |
| **P4 AI Review** | AI | `references/p4-p5-review-test.md` | 前/后端 `reviewer`（**全文加载**，优先子代理执行）、`api-contract-checker`、`similar-issue-sweep` | 逐维度结论齐备、无「未检查」、自修完毕 |
| **P5 AI 自测** | AI | 同上 + `templates/testcases.md` | backend `testing` | **先产用例文档**（按实际场景 / 回归按影响面 / 存疑先对齐）→ AI 可测项全过；台账 `待Review` |
| **P6 开发者 Review** | 开发者 | `references/p6-p8-developer-gates.md` + `templates/review-materials.md` | — | 开发者回复（ARCH 深评 / NORMAL 知会）；台账 `待验收` |
| **P7 开发者 / AI E2E** | 开发者或受托 AI | 同上 | — | 开发者说"通过"；**不通过 → 修复后重走 P4 → P7** |
| **P8 开发者确认** | 开发者 | 同上 | — | 明确"确认"才进 P9（NORMAL 并入 P6） |
| **P9 更新进度** | AI | `references/p9-p12-closeout.md` | `progress-tracker` | **硬门禁**：plan 回填 + 台账迁移，否则不得宣布完成 |
| **P10 沉淀核对** | AI + 开发者 | 同上 | `team-memory`、`capability-registry` | 五项核对清单答完 |
| **P11 提交代码** | AI | 同上 | `git-commit`（读其主文件全文） | **开发者本次授权**；开发分支；无 AI 记号 / 进度词；已推送并交接 |
| **P12 总结 + 收尾** | AI | 同上 | `dev-output`、`neat-freak` | 报告落档；**恢复卡已删**；残留删除候选经**开发者确认**才清；收尾已提交（授权范围见 `git-commit` 一） |

细则：轻量任务简化、并行会话与 Worktree → `references/flow-control.md`。

## 流程控制

### 回退规则

| 触发点 | 回退到 | 说明 |
|--------|--------|------|
| P6 第一轮（前端视觉）有问题 | P3 | 修复 → P4 → P5 第一轮 → P6 第一轮 |
| P6 第二轮（功能）有问题 | P3 | 修复 → P4 → P5 第二轮 → P6 第二轮 |
| P7 有 Bug（手测或 AI E2E） | P3 | **硬规则**：修复（含回溯扫描）→ P4 → P5（更新用例）→ P6 → P7，**禁止跳过任何一环直接复测** |
| P8 不通过 | P6 | 重新 Review |

### 进度判定、阶段回执与压缩恢复

**进度以磁盘为准**：产物文件存在与否是主要判定依据，台账两列 + 恢复卡用于交叉核对；可不落档的环节（轻量 / L1 任务的简化计划与用例）、回退返工期间和已完成区之后的阶段（P9–P12，已完成表无阶段列）以恢复卡「当前阶段」为准。会话中断续作、上下文被压缩、或不确定"现在在哪"时，按下表定位，从对应阶段继续，不重头走流程：

| 磁盘信号 | 判定阶段 |
|----------|----------|
| STATUS 无本需求条目 | P1 |
| 有条目（`规划中`），`design/{yyyy-MM-dd}_{slug}-design.md` 缺 | P3 对齐前（P2 可快速重做）；L1 简化计划可不落档，以恢复卡为准 |
| 条目 `开发中`、无设计文档（L1 / 轻量任务）、无 review 报告 | P3 编码 / P4，以恢复卡「当前阶段」为准 |
| 设计文档在，无 review 报告 `design/{yyyy-MM-dd}_{slug}-review.md`（任何级别 P4 都落档，NORMAL 可精简为逐维度结论表） | P3 编码 / P4 |
| review 报告在，`design/{yyyy-MM-dd}_{slug}-testcases.md` 缺 | P5 第 0 步；轻量任务用例不单独落档，以恢复卡为准 |
| 用例文档在且「执行记录」P5 列未填完 | P5 执行 |
| STATUS 状态 = 待Review / 待验收 | P6–P8（等开发者） |
| 状态 = 开发中 但 review 报告与用例文档都在（P6 / P7 不通过回退） | 返工中：以恢复卡「当前阶段」为准（P3 修复 → P4 → P5），不得只复测失败用例 |
| 状态 = 已完成（已完成区）且恢复卡在 | 恢复卡「当前阶段」所写的 P9 / P10 / P11 / P12；P11 的提交授权重新取得 |
| 状态 = 已完成、恢复卡已删、`developer/output/{条目名}.md` 在 | 已收尾 |
| 信号矛盾（如有用例无 review 报告、台账与恢复卡不一致、已完成且恢复卡已删但报告缺） | **停下**向开发者报告，不擅自补跑 |

**恢复卡**：`.document/plan/context/{条目名}.md`（条目名 = `{yyyy-MM-dd}_{stage}_{slug}`，**slug 取分支 business 段、与 worktree 目录名一致**，否则 `restore_context.py` 无法按分支 / 路径自动定位），P1 建、每次阶段迁移时与台账同步更新；P12 完成后删，搁置保留，取消时删（模板 `plan/context/README.md`）。只写阶段、门禁、工作位置、需重读清单、关键决策、未完成项；**不写授权**。worktree 会话同样写项目根（`git-commit` 8.4）。

**阶段回执**：每个阶段出口输出一行固定格式 `[Px ✅ | 依据 … | 下一步 Py]`（如 `[P4 ✅ | 依据 design/2026-10-30_xx-review.md 全维度 ✅、回溯 0 处 | 下一步 P5]`），与台账 / 恢复卡更新同一步——格式固定，便于压缩摘要保留。

**压缩恢复**（发现摘要、想不起当前门禁细节时，按 `red-lines.md`「压缩恢复协议」）：
1. 运行本技能 `scripts/restore_context.py`（从项目根或 worktree 内任意目录；无 Python 时手动读卡）——输出红线、本需求恢复卡、STATUS 对应行、需重读文件清单；多需求并行且定位不到时按它列出的卡名用 `--task {slug}` 指定
2. 按「需重读」重读：本主文件 + 路由表中当前阶段的子文件（P4 为 reviewer 全文）；对照上表核对恢复卡所写阶段与磁盘一致
3. 输出 `[恢复 | 需求 … | 阶段 Px | 已过 … | 下一步 …]` 再继续
4. 授权（提交 / 主干直提 / 计划批准）不从摘要继承，一律重新确认
