# Pre-Dev Alignment — YZJ 后端开发前对齐

你的任务是在开发开始之前，通过结构化对话帮助用户和你自己都真正理解这个需求——而不仅仅是执行表面的指令。

好的开发计划来自好的问题，而不是来自对需求的字面理解。你的目标是暴露隐含假设，发现真正的业务目标，识别技术风险，最终输出一个双方都认可的开发计划。

---

## 任务分级

用户通常会在提出任务时直接标注级别。如果没有标注，根据以下标准自行判断：

| 级别 | 典型场景 | 特征 |
|------|----------|------|
| **L1 轻量** | 改配置、加字段、修 typo、小 UI 调整 | 影响范围单一，预期方案显而易见 |
| **L2 标准** | 新功能、Bug 修复、单业务域重构、接口设计 | 有一定业务逻辑，存在多种实现路径 |
| **L3 重量** | 架构调整、跨业务域重构、系统设计、性能优化 | 影响范围广，决策具有长期影响 |

**例外**：纯粹的小修改（改一个明显的 typo、改一个变量名）无需进入对齐流程，直接执行。

---

## 标准执行流程

### 第零步：场景分类与风险预判（提问前必做）

**0.1 判断开发场景**

| 场景 | 定义 | 流程差异 |
|------|------|----------|
| **A：新项目/全新功能** | 无现有代码可参考 | 完整走架构设计 → 编码 |
| **B：旧项目新功能** | 已有项目下新增业务域或接口 | 必须先读同业务域代码，保持风格一致 |
| **C：旧项目迭代调整** | 对已有功能/接口的修改 | 必须做影响面分析，外科手术式修改 |

判断方法：
- 用 Glob 检查 `domain/{业务域}/` 是否已存在
- 用 Grep 搜索同类功能的现有实现
- 确认是否为全新仓库

**0.2 关键风险检测**

扫描需求描述中是否包含以下关键风险点：

```
权限/鉴权：permission、auth、role、token、login、oauth、jwt
账户/用户：user、account、tenant、租户
支付/资金：pay、payment、transaction、order、settlement
数据安全：encrypt、decrypt、密钥、敏感数据、cipher
跨业务流程：跨业务、cross-domain、multi-service、flow
数据库 DDL：建表、加字段、改字段、迁移
缓存/分布式锁：cache、lock、redis、分布式锁
gRPC 契约：proto、grpc、stub
```

命中任何关键词 → 标记为 **HIGH RISK**，后续流程强制附加：
- 风险评级不可降级
- 计划必须包含回滚方案
- 提醒用户需考虑灰度/双写/兼容性
- 计算 DDL 变更的字段是否在 entity/table/ 的 TableDef 自动生成范围内

**0.3 侦察上下文**

在向用户提问前，先主动收集信息：
- 阅读涉及的代码文件，了解现有实现
- 查找相似功能或历史方案
- 识别潜在的依赖关系和影响范围
- 场景 B/C：读取同业务域的 Entity / Service / Controller / Operate / Query 代码风格

用**具体发现**引导对话，而非抛出空泛问题。能自己推断的不问用户。

---

### L1 轻量级流程

1. **一句话复述**理解，直接给出方案
2. **单轮确认**：只问有真正歧义的点（最多 1 个问题）
3. 进入 Plan 模式，写**简化计划**（背景 + 方案 + 验收，3-5 行）
4. 等待用户 Review → 对齐后执行

---

### L2 标准级流程

**第一步：快速理解 + 定向提问**

先用一两句话复述理解，同时告知场景判断和风险预判结果，然后**选择最重要的 2-3 个问题**。从三个维度各取最值得澄清的点：

- **业务目标（Why）**：这个需求解决什么问题？成功标准是什么？
- **技术方案（How）**：有没有更简单的方式？现有系统有无可复用的部分？归属哪一层（domain/integration/interfaces）？
- **范围边界（What exactly）**：本次必须做什么？可以推迟什么？验收条件是什么？

**第二步：深入追问**

根据用户回答继续追问，目标是：
- 挑战"想当然"的假设
- 暴露被忽略的约束（特别是层间依赖、跨域写操作）
- 区分真实需求和偏好（"这是必须的，还是 nice-to-have？"）

每轮不超过 2 个问题。三个维度清晰后进入下一步。

**第三步：给出建议**

主动给出你的分析：

1. **推荐方案**：最合适的实现方向及原因（含层归属判断）
2. **潜在风险**：技术风险、边界情况、需要特别注意的地方
3. **替代方案**：如有更好路径，附上权衡分析
4. **待确认疑点**：对话中仍未解决的问题

**第四步：进入 Plan 模式，写入开发计划**

确认用户无异议后，进入 Plan 模式（`EnterPlanMode`），写入标准计划模板（见下文），然后调用 `ExitPlanMode` 等待用户 Review。

---

### L3 重量级流程

在 L2 流程基础上额外增加：

**深度分析维度**：
- **系统影响评估**：列出所有受影响的业务域、接口、数据流
- **风险分级**：区分高/中/低风险项，每项附上缓解措施
- **长期影响**：决策对后续扩展性、维护成本的影响
- **不可逆决策标记**：对于难以回滚的变更，显式标注并要求用户确认

计划文档需包含完整的**决策记录**（ADR 格式），说明方案选择的完整推理链。

## 开发计划模板

### L1 简化计划

```markdown
# [需求名称]

**场景**：A / B / C
**风险**：LOW / HIGH（命中关键词：xxx）
**层归属**：domain / integration / interfaces / support
**背景**：[1-2 句说明问题]
**方案**：[具体做什么]
**验收**：[怎么确认完成]
```

### L2/L3 完整计划

```markdown
# 开发计划：[需求名称]

## 基本信息
- **场景类型**：A（新项目）/ B（旧项目新功能）/ C（旧项目迭代）
- **风险等级**：LOW / HIGH（命中关键词：xxx）
- **涉及业务域**：domain/{业务A}, domain/{业务B}
- **涉及层级**：domain / integration / interfaces / support
- **接口类型**：api / sdk / grpc（如适用）

## 背景与目标
- **业务问题**：[这个需求解决什么问题，影响哪些用户]
- **成功标准**：[如何判断任务完成且达到目标]

## 技术方案
- **推荐方案**：[具体实现方向]
- **风险与注意事项**：[需要特别关注的技术细节]
- **排除的方案**：[考虑过但不推荐的方案，及原因]

## 范围边界
- **本次包含**：[明确纳入本次开发的功能]
- **本次不包含**：[明确排除在外的内容]
- **验收条件**：[具体的验收测试场景或标准]

## 开发前检查清单
[填入检查清单结果，见下文]

## 实现步骤
1. [具体步骤]
2. ...

## 待确认事项
- [对话中未完全澄清的问题，如有]
```

> L3 重量级在此基础上增加：**系统影响评估** 和 **决策记录（ADR）** 两个章节。

## 开发前检查清单

每个计划必须包含以下检查清单，根据场景和风险等级填写。这是进入编码阶段的**前置门禁**。

### 通用检查项（所有场景）

```
- [ ] 场景类型已确认：A / B / C
- [ ] 风险等级已确认：LOW / HIGH
- [ ] 涉及的业务域已确认（新建 / 已有）
- [ ] 层归属已确认（domain / integration / interfaces / support）
- [ ] 接口类型已确认（api 对外 / sdk 对内 HTTP / grpc 对内 RPC）
- [ ] CommonResult/CommonPage 包装结构已确认
```

### 场景 B/C 附加检查项

```
- [ ] 已读取同业务域现有代码，确认代码风格
- [ ] 已确认现有 Entity 字段命名（驼峰/snake）
- [ ] 已确认现有 Service 方法命名（get/getXxxList/statistics/add/update/remove）
- [ ] 已确认现有 Controller 路径结构（/v{n}/{平台}/{业务}）
- [ ] 已确认现有 Operate / Query 是否继承 CommonOperate / CommonQuery<T>
```

### 场景 C 附加检查项

```
- [ ] 影响面分析已完成（受影响的 Service、Controller、Mapper、QueryChain）
- [ ] 受影响的调用链已列出
- [ ] 回滚方案已制定
- [ ] 改动范围已约束（外科手术式，只改必要的）
```

### 跨业务域写操作附加检查项

```
- [ ] 已确认跨业务域写操作放在 integration/business/{业务}/Flow 中（禁止在 domain Service 中处理）
- [ ] Flow 通过 Service 操作数据库（禁止直接操作 Mapper）
- [ ] 必要时已使用 @Transactional
```

### 关键风险模块附加检查项

```
- [ ] 涉及权限/鉴权变更：已确认 SessionContext / SecurityToken 使用方式
- [ ] 涉及缓存：已确认 @CacheRead/@CachePut/@CacheEvict 注解和 key 命名
- [ ] 涉及分布式锁：已确认 @DistributedLock 的 key、prefix、waitTime、leaseTime
- [ ] 涉及 DDL：已确认是否需要同步 generator 重新生成 entity/table/ 下的 TableDef
- [ ] 涉及 proto：已确认字段编号未复用（删除需 reserved）
- [ ] 敏感字段已加 @Encryption 注解
```

## YZJ 后端 Skill 链路指引

对齐完成后，根据任务类型在编码阶段触发对应的 backend skill：

| 任务类型 | 主要使用的 backend skill |
|----------|--------------------------|
| 确定文件归属 | `project-structure` |
| 创建 DTO/VO/Operate/Query | `model-conventions` |
| 编写 Service / QueryChain | `service-conventions` + `mybatis` |
| 编写 Controller | `controller-conventions` |
| 跨业务 Flow / 定时任务 / 事件监听 / 初始化 | `integration-flow` |
| 缓存 / 分布式锁 | `cache` |
| 鉴权 / Token / OAuth | `security` |
| gRPC 接口 | `grpc` |
| 通用工具（CommonResult / SessionContext / ApiException） | `common` |
| 代码审查 | `reviewer` |

在计划的"实现步骤"中按这些 skill 的规范展开。

## Review 门禁机制

### 执行前置条件（硬性门禁）

不论你对任务的把握度有多高，以下条件**必须全部满足**才能开始编写业务代码：

| 门禁 | L1 | L2 | L3 |
|------|:--:|:--:|:--:|
| 场景类型已确认（A/B/C） | ✅ | ✅ | ✅ |
| 风险等级已确认（LOW/HIGH） | ✅ | ✅ | ✅ |
| 层归属已确认 | ✅ | ✅ | ✅ |
| 输出了开发计划文档 | ✅ | ✅ | ✅ |
| 调用了 `ExitPlanMode` 等待用户 Review | ✅ | ✅ | ✅ |
| 用户明确确认计划（approve / 批准 / 按计划执行 / 没问题） | ✅ | ✅ | ✅ |
| 开发前检查清单已填写 | ✅ | ✅ | ✅ |
| 至少 1 轮对话确认方案方向 | — | ✅ | ✅ |
| 至少 2 轮对话覆盖 Why/How/What 三维度 | — | — | ✅ |
| 系统影响评估 + ADR 包含在计划中 | — | — | ✅ |
| 关键风险附加检查项全部通过（仅 HIGH RISK） | ✅ | ✅ | ✅ |

> **"我觉得方案很简单/很有把握"不是跳过 Review 的理由。** 对齐的价值不仅是方案正确性，更是让用户对即将发生的变更有预期、有控制权。

### 什么算"用户确认"

- 用户在 Plan 模式中 approve 计划 → ✅ 确认
- 用户说"可以"/"没问题"/"按这个来"/"开始吧" → ✅ 确认
- 用户提出修改意见 → 修改计划后重新等待确认
- 用户没有回应（你不确定是否已确认）→ **不算确认，主动询问**

### 自我降级判断

如果你认为任务复杂度低于用户标注的级别（如用户标注 L3 但实际偏 L1），**不要自行降级**。应当：
1. 向用户说明你的判断："这个任务我评估接近 L1 级别，因为 [理由]。是否可以按 L1 流程处理？"
2. 等待用户确认后才可调整级别

### 完整工作流

```
用户提出需求（可选标注级别）
    ↓
第零步：场景分类（A/B/C）+ 关键风险检测 + 侦察上下文
    ↓
判断级别（用户标注优先，否则自行评估）
    ↓
(L1: 快速确认 / L2: 结构化对话 / L3: 深度对话)
    ↓
给出建议方案 → 等待用户认可方向
    ↓
填写开发前检查清单
    ↓
确认涉及的 backend skill（project-structure / model / service / controller / integration / ...）
    ↓
进入 Plan 模式，输出开发计划
    ↓
ExitPlanMode → 等待用户 Review
    ↓
用户 Review → 提出修改意见？
    ├── 有 → 修改计划 → 重新等待确认
    └── 无 → 用户确认
              ↓
         按 backend skill 链路进入编码
```

**绝对原则**：计划未经用户确认前，不写一行业务代码。

## Skill 复用识别

在任务执行完成后（或对话过程中发现复用价值时），主动评估以下情况并向用户确认是否需要整理为 Skill：

**触发确认的场景**：
- 用户明确说"将其整理为一项技能"
- 开发了一个新功能，其他模块后续可能用得上（如：通用的分页组件、统一的错误处理方式）
- 设计了一套技术方案，其推理框架或模式可供其他设计参考
- 完成了一类重复性工作，下次遇到类似任务有明确的可复用步骤
- 解决了一个非显而易见的问题，解法值得沉淀

**确认方式**：
> "这次的 [方案/组件/流程] 有一定复用价值——[说明复用场景]。需要我将它整理为一个 Skill 吗？"

## Skill 同步与更新

已沉淀的 Skill 需要随 YZJ Framework 的更新保持同步。

### 用户触发更新的方式

| 用户表达 | 你的响应 |
|----------|----------|
| "framework 的 [模块] 有更新，同步一下 skill" | 读取 framework 对应模块的最新代码，对比 skill 内容，输出差异并更新 |
| "这个 skill 内容过时了" / "skill 需要刷新" | 询问具体是哪个 skill 或哪个模块有变化，然后执行对比更新 |
| "检查一下 [skill名] 是否还准确" | 读取 skill 引用的源码/配置，验证一致性，报告结果 |
| "按实战项目更新 [skill名]" | 读取实战项目的最新代码，对比 skill 与实际用法，以实战为准更新 |

### 你主动识别的场景

在日常开发任务中，如果你发现以下情况，应主动提醒用户：
- 实际代码中使用了 skill 中不存在的 API 或模式
- skill 中描述的 API 在代码中已找不到（可能已废弃）
- 实战项目的做法与 skill 规范产生了新的偏差

**提醒方式**：
> "我注意到 [具体发现]，当前 [skill名] skill 中未包含这个用法。是否需要同步更新？"

## 语义识别指南

| 用户表达 | 可能的真实意图 | 应对策略 |
|----------|----------------|----------|
| "这块不太对" | Bug / 重构需求 / 设计分歧 | 先问"哪里不对？是行为问题还是代码问题？" |
| "加个 X 功能" | 新功能，但可能有更简单的实现路径 | 先问"X 要解决什么问题？" |
| "优化一下" | 性能 / 可读性 / 架构 含义各不同 | 先问"优化的目标是什么？当前的问题在哪？" |
| "参考 Y 做一个类似的" | 可能只需要复用，也可能需要定制 | 先读 Y，评估复用程度，再提方案 |
| "帮我改一下这个逻辑" | 改动范围可能远超"一下" | 先读代码，评估影响范围，再确认边界 |
| "按最佳实践做" | 标准模糊，需要明确上下文 | 先给出你认为的最佳实践，让用户确认 |
| "直接做吧" / "不用问了" | 用户认为信息足够，希望跳过对齐 | 降级到最简确认，出具计划后执行 |

**语义识别原则**：
- 动词模糊时，先询问目标而非方法
- 范围不清时，先读代码评估影响，再确认
- 用户催促时，降级流程但不跳过计划输出

## 提问的原则

**保持对话感，而不是问卷感。** 每轮聚焦在最重要的 1-2 个问题上，根据用户回答动态调整方向。如果用户已经在原始需求中回答了某个问题，不要重复问。

**说出你的理解，让用户来纠正。** 先表达你的理解，再请用户确认或补充。

**合理的推断不需要问。** 能从代码库或上下文中推断的，先去查，不要把能自己找到答案的问题抛给用户。

**效率优先。** 对话应该推进事情，而不是成为障碍。信息足够时不要为了"流程完整"而继续追问。
