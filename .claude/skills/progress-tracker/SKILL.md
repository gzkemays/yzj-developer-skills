# 项目进度维护（progress-tracker）

> 核心原则：**进度状态迁移时当下更新，不攒到收尾**。台账是并行开发下
> 团队（以及所有 AI 会话）判断"现在谁在做什么、做到哪了"的唯一可信来源。

---

## 一、两层进度模型

| 层级 | 载体 | 粒度 | 更新时机 |
|------|------|------|----------|
| **需求级** | `.document/plan/STATUS.md` 台账 | 一条需求一行 | 状态每次迁移时**立即** |
| **任务级** | `.document/plan/{模块}.md` 任务清单 | 一个任务一个 checkbox | 状态实际变化时**即时回填**（完成 / 废弃 / 调整），最迟提交前；P9 核对、P11 自检（见「任务清单回填约定」） |
| **待立项** | `.document/plan/backlog-{topic}.md` | 一个被推迟 / 砍掉的主题一份 | 对齐或 Review 中砍范围、台账搁置时**当场落档** |

---

## 二、需求进度台账（STATUS.md）

### 文件模板

```markdown
# 需求进度台账

> 任何开发 session 开始前必读；需求状态迁移时必须立即更新本文件。
> 条目命名与 output 报告一致：{yyyy-MM-dd}_{stage}_{slug}（日期 = 需求启动日）。
> 容量红线：进行中 ≤ 20 条（超限先由开发者裁决再开新需求）；已完成保留近 20 条（溢出归档到 STATUS-ARCHIVE.md）。
> 最后更新：{yyyy-MM-dd HH:mm}

## 进行中

| 需求 | 状态 | 负责人 | 计划文档 | 涉及模块 | 最近动态 |
|------|------|--------|----------|----------|----------|
| 2026-06-06_P4_ai-closed-loop-orchestration | 开发中 | 张三 | plan/30-xxx.md | ai / workitem / document | 06-08 P5 自测通过 |
| 2026-06-03_P4_ai-doc-auto-index | 待Review | 李四 | plan/29-xxx.md | ai / document | 06-07 P6 材料已出 |

## 已搁置 / 已取消

| 需求 | 状态 | 原因与恢复条件 |

## 已完成（倒序，保留近 20 条）

> 更早的条目见 [STATUS-ARCHIVE.md](STATUS-ARCHIVE.md)（原文照搬 + 落档链接 + 按业务域检索索引）。

| 需求 | 完成日期 | 报告 |
| 2026-06-01_P4_ai-technical-solution-gen | 2026-06-02 | output/2026-06-01_P4_ai-technical-solution-gen.md |
```

### 状态机

```
规划中 → 开发中 → 待Review → 待验收 → 已完成
            │          │          │
            └──────────┴──────────┴──→ 已搁置（写明原因与恢复条件）/ 已取消
```

| 状态 | 含义 | 进入条件 |
|------|------|----------|
| `规划中` | 对齐/方案设计中，未编码 | pre-dev-alignment 启动 |
| `开发中` | 编码 + AI 自审自测中（P3-P5） | 编码前评审门禁通过（L2 技术设计 / L3 需求+技术设计） |
| `待Review` | 等开发者 Review（P6） | P5 自测通过 |
| `待验收` | 等开发者测试/确认（P7-P8） | P6 通过 |
| `已完成` | 验收通过且 P9-P12 收尾完毕 | P8 确认 + 报告产出 |
| `已搁置` | 暂停，**必须写原因与恢复条件** | 开发者决定 |

### 台账规则

1. **「最近动态」一栏带日期**，一句话写最近一次实质进展——其他会话靠它判断是否可以接手/是否阻塞
2. **并行冲突显性化**：「涉及模块」一栏列出业务域/模块；新需求启动时与进行中条目比对，模块重叠 → 在 P1 向开发者提示潜在冲突（文件冲突、契约冲突、互相覆盖）
3. **完成的定义**：只有 P8 验收通过且报告产出后才能迁移到"已完成"——AI 自测通过 ≠ 完成
4. **不允许幽灵需求**：编码超过一个 session 的需求必须在台账有条目；发现正在做的事不在台账上 → 先补登记再继续
5. **行内瘦身**：「最近动态」控制在 3 行以内——只写结论 + 落档指针（plan / design / output / memory 链接），过程细节写进对应文档。台账行持续膨胀 = 该需求缺落档文档的信号，先补文档再瘦身
6. **搁置 / 砍范围必落 backlog**：需求被搁置，或对齐 / Review 阶段主动砍掉、推迟的 Phase / 功能点，除在台账写原因与恢复条件外，必须同步落一份可独立阅读的 `plan/backlog-{topic}.md`（格式见下「backlog 文档」），台账行只放指针——"推迟"若没有文档承接，等于"遗忘"

### 台账容量治理（硬规则）

台账是给**当下开发**用的工作面板，不是历史档案。两条容量红线保证它始终轻、可一屏检索：

**红线 1：「进行中」（含规划中）不得超过 20 条**

- **检查时机**：session 开始读台账时（`iteration-planner` Step 1）+ P1 登记新条目前
- 超限（或本次登记后将超限）→ **暂停登记新需求**，向开发者输出裁决清单：全部进行中条目按「最近动态」日期倒序排列，**30 天以上无实质动态的标记「疑似弃用」**
- 开发者逐条裁决：继续保留 / 迁「已搁置」（必须写原因与恢复条件）/ 迁「已取消」/ 合并到其他条目
- 若开发者判断没有可弃用项 → 由开发者指定**收尾优先级**（先推动哪些条目到已完成）后方可登记新条目
- **AI 不得自行搁置或取消任何条目**；开发者未裁决前，新需求不登记、不编码

**红线 2：「已完成」只保留近 20 条，溢出必须归档**

- **检查时机**：P9 把条目迁入「已完成」后立即计数
- 超过 20 条 → 把最旧的溢出条目移入同目录 `STATUS-ARCHIVE.md`（首次归档时按下方骨架创建），归档规范：
  1. **原文照搬**：整行一字不改地搬运——台账行内文字往往是该条目唯一的过程记录，禁止概括压缩
  2. **落档校验（归档门禁）**：逐条核对至少有一个真实存在的落档链接（output 报告 / design / plan / adr / memory 之一）；
     **无落档的条目不得归档**——先按台账行内容补一份最小存根文档（落 `developer/output/`），补链后再移
  3. **维护检索索引**：归档文件头部维护「按业务域检索」索引（业务关键词 → 条目锚点），新归档条目挂进对应业务域
  4. 归档文件头部追加本次归档批次记录（日期 + 移出条数）

**STATUS-ARCHIVE.md 骨架**（首次归档时创建）：

```markdown
# 需求进度台账 · 已完成归档

> 本文件是 [STATUS.md](STATUS.md)「已完成」表的溢出归档：原文照搬、一字不改。
> 检索指引：按业务关键词 grep 本文件与 developer/output/、design/ 目录。
> 归档批次：{yyyy-MM-dd} 移出 {N} 条

## 按业务域检索

- **{业务域}**：[`{条目名}`](#锚点) · …

## 归档明细（按完成日期倒序，原文照搬）

### {条目名}
**完成日期**：{yyyy-MM-dd} ｜ **落档**：[{文档}]({路径})
**原台账记录**（原文照搬）：{整行内容}
```

> 落档校验能成立的前提是**每个需求开发前后都有文档**——编码前由 `pre-dev-alignment` 文档门禁保证（需求对齐不可跳过），
> 收尾由 `dev-session` P12 成果报告保证。跳过对齐、盲目设计开发的需求会在归档时被拦下，事后补档的成本远高于当时就写。

### 任务清单回填约定（DoD，硬规则）

模块文档里的任务清单是接手人判断"哪些做了、哪些没做"的第一依据。状态**实际发生变化时即时回填**，最迟在提交前完成，不囤到迭代收尾：

| 变化 | 回填动作 |
|------|----------|
| 任务完成（P8 验收通过） | `- [ ]` → `- [x]` |
| 方案废弃 / 回滚 / 砍范围 | `- [ ]` → `- [⛔]`，行尾写 `（已废弃：原因；替代：方案或 backlog 链接）`——**不能留 `[ ]` 让人以为还要做，更不能留 `[x]`** |
| 实现与描述有出入（路径 / 字段 / 方案调整） | 当场改任务描述，不留与代码不符的文字 |
| 清单外的额外交付 | 补一行再勾，不做"清单外的隐形工作" |
| 阻塞出现 / 解除 | 行尾标注 `（阻塞：原因）`，解除后删掉 |

- **提交前 DoD**：「任务清单与实际代码一致」是每次提交（dev-session P11）的完成定义——P9 核对、P11 自检必查此项
- 反例（已发生）：多个已落地任务长期标"待开始"、已回滚的任务仍标"已完成"，接手人只看清单就严重误判进度——**失真的清单比没有清单更危险**

### backlog 文档（推迟即落档）

`.document/plan/backlog-{topic}.md`，一个主题一份，必须**可独立阅读**、能直接作为下次 `pre-dev-alignment` 的输入：

```markdown
# Backlog：{主题}

**状态**：待立项 / 已立项（→ 台账条目 {名称}）　**记录日期**：{yyyy-MM-dd}　**影响端**：前端 / 后端 / 联动
**触发来源**：{哪个需求的对齐 / 哪次 Review 砍下来的，附链接}

## 已实现 vs 缺失（逐项核对）
| 能力点 | 现状 | 缺失 |
|--------|------|------|

## 待拍板岔路
- {方案 A vs B，各自代价与影响}

## 建议工作流
- {直接走 pre-dev-alignment L2 / 需先出 ADR / 依赖 XX 完成后再做}
```

- **盘点待办必扫**：回答"某模块还有哪些待办"时，扫描范围 = 模块文档未勾任务 **＋** `plan/backlog-*.md` 相关主题，二者并列；只看模块文档会漏掉被砍的部分
- **立项时**：在台账登记条目，backlog 状态改「已立项」并指向台账条目；需求完成后 backlog 文件保留，作为"当初为什么推迟"的决策记录

## 三、模式 A：开发前确认（dev-session P1）

1. **读台账**：列出进行中条目 → 向开发者同步"当前并行需求 + 各自状态"；检查本任务是否已登记；
   **统计进行中条目数，超 20（或登记后将超）→ 先走「台账容量治理」红线 1 的裁决流程，裁决完成前不登记不编码**
2. 定位目标模块文档，解析 `- [ ]` / `- [x]` / `- [⛔]` 条目，输出模块进度统计（完成数/总数，按 接口层/业务层/集成层/数据库 与 页面/组件/Store/API 分类，已废弃项单列）；扫 `plan/backlog-*.md` 中与本模块相关的待立项主题，一并带进范围确认
3. 确认本次 session 计划完成的任务范围
4. 台账登记本需求（或更新状态为 `开发中`）

## 四、模式 B：开发后更新（dev-session P9，硬门禁）

1. 对照 session 内变更文件 + `git diff --name-only` 确认实际完成的任务
2. 模块文档：按「任务清单回填约定」核对——完成 `- [x]`、废弃 `- [⛔]`（含原因与替代）、描述与实现不符当场改、清单外交付补行；更新文档顶部 `状态` 与 `最后更新`；本次砍掉 / 推迟的内容已有 `backlog-*.md` 承接
3. 台账：本需求条目迁移状态；`已完成` 则移入已完成区并附报告链接；
   **移入后计数已完成区，超 20 条 → 按「台账容量治理」红线 2 归档溢出条目（含落档校验）**
4. 模块全部完成 → 更新 `00-plan-overview.md` 阶段状态
5. 输出进度摘要（本次完成 N 项 / 模块进度 / 剩余任务 / 下一步建议）

> **不乐观标记**：只勾选确实完成且通过验收的任务。

## 五、模式 C：状态即时迁移（全程）

P5 通过 → `待Review`；P6 通过 → `待验收`；P8 通过 → 走模式 B 完整收尾。
每次迁移只改台账一行 + 「最近动态」+「最后更新」时间戳，开销 < 1 分钟，**不允许以"等下一起更新"为由跳过**。
任务级同理：任务完成 / 废弃 / 阻塞发生时即时回填模块文档（见「任务清单回填约定」），P9 只做核对不做补救。

## 六、批量进度查看

用户问"整体进度"时：读台账 + 所有模块文档，输出汇总表（阶段 × 模块 × 前后端进度 × 状态）+ 进行中需求清单 + 待立项 backlog 清单（`plan/backlog-*.md`，含记录日期与触发来源）。
