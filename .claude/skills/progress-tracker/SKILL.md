# 项目进度维护（progress-tracker）

> 核心原则：**进度状态迁移时当下更新，不攒到收尾**。台账是并行开发下
> 团队（以及所有 AI 会话）判断"现在谁在做什么、做到哪了"的唯一可信来源。

---

## 一、两层进度模型

| 层级 | 载体 | 粒度 | 更新时机 |
|------|------|------|----------|
| **需求级** | `.document/plan/STATUS.md` 台账 | 一条需求一行 | 状态每次迁移时**立即** |
| **任务级** | `.document/plan/{模块}.md` 任务清单 | 一个任务一个 checkbox | 开发确认通过后（P9） |

---

## 二、需求进度台账（STATUS.md）

### 文件模板

```markdown
# 需求进度台账

> 任何开发 session 开始前必读；需求状态迁移时必须立即更新本文件。
> 条目命名与 output 报告一致：{yyyy-MM-dd}_{stage}_{slug}（日期 = 需求启动日）。
> 最后更新：{yyyy-MM-dd HH:mm}

## 进行中

| 需求 | 状态 | 负责人 | 计划文档 | 涉及模块 | 最近动态 |
|------|------|--------|----------|----------|----------|
| 2026-06-06_P4_ai-closed-loop-orchestration | 开发中 | 张三 | plan/30-xxx.md | ai / workitem / document | 06-08 P5 自测通过 |
| 2026-06-03_P4_ai-doc-auto-index | 待Review | 李四 | plan/29-xxx.md | ai / document | 06-07 P6 材料已出 |

## 已搁置 / 已取消

| 需求 | 状态 | 原因与恢复条件 |

## 已完成（倒序，保留近 20 条，更早的看 output/ 目录）

| 需求 | 完成日期 | 报告 |
| 2026-06-01_P4_ai-technical-solution-gen | 2026-06-02 | output/2026-06-01_P4_ai-technical-solution-gen.md |
```

### 状态机

```
规划中 → 开发中 → 待Review → 待验收 → 已完成
            │          │          │
            └──────────┴──────────┴──→ 已搁置（写明原因与恢复条件）/ 已取消
```

| 状态 | 含义 | 进入条件 |
|------|------|----------|
| `规划中` | 对齐/方案设计中，未编码 | pre-dev-alignment 启动 |
| `开发中` | 编码 + AI 自审自测中（P3-P5） | 编码前评审门禁通过（L2 技术设计 / L3 需求+技术设计） |
| `待Review` | 等开发者 Review（P6） | P5 自测通过 |
| `待验收` | 等开发者测试/确认（P7-P8） | P6 通过 |
| `已完成` | 验收通过且 P9-P12 收尾完毕 | P8 确认 + 报告产出 |
| `已搁置` | 暂停，**必须写原因与恢复条件** | 开发者决定 |

### 台账规则

1. **「最近动态」一栏带日期**，一句话写最近一次实质进展——其他会话靠它判断是否可以接手/是否阻塞
2. **并行冲突显性化**：「涉及模块」一栏列出业务域/模块；新需求启动时与进行中条目比对，模块重叠 → 在 P1 向开发者提示潜在冲突（文件冲突、契约冲突、互相覆盖）
3. **完成的定义**：只有 P8 验收通过且报告产出后才能迁移到"已完成"——AI 自测通过 ≠ 完成
4. **不允许幽灵需求**：编码超过一个 session 的需求必须在台账有条目；发现正在做的事不在台账上 → 先补登记再继续

## 三、模式 A：开发前确认（dev-session P1）

1. **读台账**：列出进行中条目 → 向开发者同步"当前并行需求 + 各自状态"；检查本任务是否已登记
2. 定位目标模块文档，解析 `- [ ]` / `- [x]` 条目，输出模块进度统计（完成数/总数，按 接口层/业务层/集成层/数据库 与 页面/组件/Store/API 分类）
3. 确认本次 session 计划完成的任务范围
4. 台账登记本需求（或更新状态为 `开发中`）

## 四、模式 B：开发后更新（dev-session P9，硬门禁）

1. 对照 session 内变更文件 + `git diff --name-only` 确认实际完成的任务
2. 模块文档：`- [ ]` → `- [x]`；更新文档顶部 `状态` 与 `最后更新`；实现与文档描述有差异（如 API 路径调整）→ **同步修正文档描述**；开发中发现的遗漏任务 → 追加到对应分类
3. 台账：本需求条目迁移状态；`已完成` 则移入已完成区并附报告链接
4. 模块全部完成 → 更新 `00-plan-overview.md` 阶段状态
5. 输出进度摘要（本次完成 N 项 / 模块进度 / 剩余任务 / 下一步建议）

> **不乐观标记**：只勾选确实完成且通过验收的任务。

## 五、模式 C：状态即时迁移（全程）

P5 通过 → `待Review`；P6 通过 → `待验收`；P8 通过 → 走模式 B 完整收尾。
每次迁移只改台账一行 + 「最近动态」+「最后更新」时间戳，开销 < 1 分钟，**不允许以"等下一起更新"为由跳过**。

## 六、批量进度查看

用户问"整体进度"时：读台账 + 所有模块文档，输出汇总表（阶段 × 模块 × 前后端进度 × 状态）+ 进行中需求清单。
