# 研发生命周期（dev-session）

> 所有开发任务统一走此流程。AI 自主推进 P1-P5 和 P9-P12，P6-P8 按变更分级决定开发者参与深度。
> 项目专有信息（仓库路径、构建命令、设计系统、契约约定）以项目根 `CLAUDE.md` 为准，本 skill 只定义流程。

```
┌─ AI 自主执行 ──────────────────────────────────────────────┐
│ P1  分析需求     读台账 + 计划文档，确认范围与变更级别        │
│ P2  加载沉淀     团队 memory + 能力登记册 + ADR + 个人 memory │
│ P3  开发需求     pre-dev-alignment（文档+评审门禁）→ 编码      │
│ P4  AI Review    前/后端 reviewer 硬流程 + 同类问题回溯       │
│ P5  AI 自测      前端双轮（MOCK+接口）；后端编译/测试          │
├─ 开发者参与（按变更分级）──────────────────────────────────┤
│ P6  开发者 Review   ARCH 深度评审 / NORMAL 知会式确认         │
│ P7  开发者测试      按 P5 测试用例验收（NORMAL 可选）          │
│ P8  开发者确认      硬门禁，必须明确授权                      │
├─ AI 收尾（不可省略，未完成不得宣布任务结束）─────────────────┤
│ P9  更新进度     plan 勾选 + STATUS.md 台账（硬门禁）         │
│ P10 沉淀核对     纠正/能力/漏检/文档 四项核对清单             │
│ P11 提交代码     按仓库分别 commit                           │
│ P12 总结成果     dev-output 报告到 output/                   │
└────────────────────────────────────────────────────────────┘
```

---

## 全程规则（凌驾于任何单阶段之上）

### 规则 1：纠正即沉淀

**开发者在任何阶段纠正 AI**（否决方案、指出代码问题、提醒规范、推翻设计），处理顺序固定为：

1. 完成本次修正；
2. **立即**按 `team-memory` skill 写入/更新 feedback memory（含开发者原话 + Why + How to apply），更新 `MEMORY.md` 索引；
3. 在响应中告知："已沉淀至 memory：`{文件名}`"。

**禁止**把沉淀推迟到 P10 再做——P10 只做核对，不做补救。同一问题被纠正第二次 = 沉淀机制失效，必须在 memory 中升级该条目为强约束（加入对应 reviewer 的漏检史）。

### 规则 2：修复必回溯

任何 **bug 修复、规范违规修正、优化点处理**落地后，必须按 `similar-issue-sweep` skill 执行同类问题回溯：提取问题模式 → 全库扫描 → 同类位置一并修复或列清单报告。只修被指出的那一处 = 流程违规。

### 规则 3：进度实时更新

需求状态发生迁移（开始开发 / 进入待 Review / 验收通过 / 搁置）时，**当下**更新 `.document/plan/STATUS.md` 台账（见 `progress-tracker` skill），不等收尾。多人/多会话并行开发时，台账是唯一可信的进度来源。

### 规则 4：P4 不可跳过（硬门禁）

任何 P3 编码（含"小修复 / 改一行 / 修个 bug"）完成后、进 P5 自测前，**必须**跑一次前/后端 reviewer 硬流程。"改动小 / 有把握"不是跳过理由。

## 变更分级（P1 判定，决定 P6-P8 深度）

| 级别 | 判定标准（命中任一即是） | P6 | P7 | P8 |
|------|--------------------------|----|----|----|
| **ARCH 架构级** | 影响整体架构或框架设计；新增/调整核心数据模型；安全、权限、鉴权、资金；跨业务域流程（Flow）；对外契约变更（API 破坏性调整 / proto）；开发者标注"重要需求"；不可逆变更（数据迁移、删字段） | 深度评审：开发者逐项审阅 Review 材料 + 关键代码 | 必须执行 | 必须明确授权 |
| **NORMAL 常规级** | 常规需求开发与迭代：新增页面/接口/字段、普通 bug 修复、样式调整、文案/i18n | 知会式确认：AI 输出精简摘要（变更点 / 自审结论 / 风险点），开发者**过目**后任意明确回复即过 | 开发者自行决定是否抽测 | 简化为与 P6 合并的一次确认 |

**拿不准时按 ARCH 处理。** 分级结果在 P1 出口明示开发者，开发者可以改判。

> 设计意图：开发者掌控方向与架构，把注意力从逐行 review 中释放出来；AI 用更严格的自审（P4 硬流程 + 回溯扫描）换取常规变更的自主权。NORMAL 级自审出现漏检被开发者捕获时，按规则 1 沉淀并在 memory 中记录——连续漏检的同类变更自动升级为 ARCH 级。

---

## P1：分析需求

**执行者**：AI | **关联 skill**：`iteration-planner`、`progress-tracker`

1. 读取 `.document/plan/STATUS.md` 台账：当前**进行中**的需求有哪些（含其他人/其他会话并行项）、本任务是否已在台账中
2. 读取 `.document/plan/00-plan-overview.md` 定位当前迭代阶段；读取用户指定的模块文档，解析未完成任务
3. 若用户未指定任务，列出当前阶段未完成模块供选择
4. **并行冲突检查**：若本任务与台账中其他进行中需求涉及相同模块/文件，明确提示开发者潜在冲突
5. 判定变更级别（ARCH / NORMAL），连同开发范围一句话向开发者确认
6. 在台账登记/更新本需求条目为 `开发中`（命名 `{yyyy-MM-dd}_{stage}_{slug}`，与 output 报告同名）

**出口**：开发范围 + 变更级别已确认，台账已登记

---

## P2：加载沉淀

**执行者**：AI | **关联 skill**：`team-memory`、`capability-registry`

1. 读取 `.document/developer/memory/MEMORY.md`，按任务关键词定位相关 memory 并**读取全文**（feedback 类强约束必读）
2. 读取 `.document/developer/capability/CAPABILITY.md` 能力登记册：本次涉及的功能是否已有**可复用的组件 / 工具 / 业务流程 / 既有接口**——有则优先复用，禁止重复造轮子
3. 检查 `.document/adr/` 是否有相关架构决策
4. 读取个人 memory（`~/.claude/projects/` 下）
5. 向开发者一句话总结：命中的关键约束 + 可复用能力清单（如有）

**出口**：相关沉淀与可复用能力已加载并告知开发者

---

## P3：开发需求

**执行者**：AI（架构决策暂停等待开发者）

### 文档产出与评审门禁（编码前，按 `pre-dev-alignment`）

执行 `pre-dev-alignment`（技术栈/场景/风险判断 + 任务分级 + 结构化对话），再按任务级别走**编码前文档产出与评审门禁**——**门禁未过不写业务代码**：

| 级别 | 编码前产出 | 门禁顺序 |
|------|------------|----------|
| **L1** | 简化计划 | 用户确认方案 → 编码 |
| **L2** | 技术设计文档（`design/`） | **开发者技术审核 + 二次评估** → 编码 |
| **L3** | 需求/调整文档（`plan/`）→ 技术设计文档（`design/`） | **① 用户复核需求/调整文档**（确保需求最终对齐）→ **② 开发者技术审核 + 二次评估** → 编码 |

- **二次评估**：开发者基于技术设计文档，对方案合理性 / 工作量 / 风险 / 影响面在需求初评之上再确认一次——这是**编码前对技术设计**的审核，区别于 P6 **编码后对代码**的 Review。
- **视觉交互 DEMO（按需）**：用户要求视觉方案 / 全新无参照视觉时，技术设计阶段附带产出 `design/{slug}-demo.html` 或用前端既有组件搭 DEMO；定稿后由 AI 判断是否抽为复用组件并登记 `CAPABILITY.md`（详见 `pre-dev-alignment`「视觉交互 DEMO」）。
- **对齐结论落档**：每道门禁通过后**立即**按 `pre-dev-alignment` 落档规则写入对应目录（需求文档→`plan/`、技术设计文档→`design/`、重大架构决策→`adr/`）——口头对齐不落档 = 未对齐。

### 后端路径

- 按 `yzj-dev-workflow` 流程，编码前过其门禁清单，过程中按需引用 backend 子 skill
- 工作目录：后端仓库（项目 CLAUDE.md 定义）

### 前端路径

- 按 frontend 的 `view-conventions` 等 skill 编码，遵循项目 CLAUDE.md 的设计系统约定
- 工作目录：前端仓库（项目 CLAUDE.md 定义）

**前端两轮开发机制**（接口未就绪时）：
- **后端接口未就绪** → 双轮：第一轮基于 MOCK 实现视觉/交互层（在 service 层用环境开关条件分支返回 mock，要求"删除/翻转一处即可切换真实接口"，不引入难剥离的 mock 框架）；P5/P6 第一轮通过后回到 P3 对接接口，再走 P5/P6 第二轮
- **后端接口已就绪** → 单轮：直接对接，P5/P6 合并视觉与接口验证

> 与编码前的**视觉交互 DEMO** 区分：DEMO 在 P3 文档阶段定视觉 / 交互**方向**；MOCK 轮是**真实页面实现**。DEMO 已抽成复用组件的，MOCK 轮直接复用，不重复造。

### 全栈路径

1. 先后端 → 后前端（后端完成不暂停，直接进前端）
2. 运行 `api-contract-checker` 检查前后端契约一致性
3. P6-P8 在前后端全部完成后统一触发

**出口**：代码实现完成

---

## P4：AI Review

**执行者**：AI | **关联 skill**：backend `reviewer`、frontend `reviewer`、`api-contract-checker`、`similar-issue-sweep`

1. **后端**：按 backend `reviewer` 的**七步硬流程**执行（含进入前的 echo 协议、强制 Grep 扫描、漏检史核对），逐维度 × 逐文件全覆盖，**禁止选择性抽查**
2. **前端**：按 frontend `reviewer` 的七步硬流程执行，同样全覆盖
3. **跨端**：涉及接口的变更运行 `api-contract-checker`
4. **同类问题回溯**：本次变更若属于修复/纠正类，按 `similar-issue-sweep` 扫描全库同类问题（规则 2）
5. 发现问题 → **自行修复** → 重跑对应扫描验证无回归，不留给开发者

**出口**：审查报告（逐维度结论）+ 回溯扫描结果，所有可自修问题已修复

---

## P5：AI 自测

**执行者**：AI

### 后端

- 执行项目 CLAUDE.md 定义的编译/测试命令（如 `mvn compile -pl {module} -am -q`）
- 失败 → 修复 → 重试，直到通过

### 前端 —— 两轮自测机制

推荐使用 Claude Preview MCP（`preview_start` / `preview_snapshot` / `preview_console_logs` / `preview_network` 等）；项目无 preview 工具时退化为 `build + 类型检查 + 手动验证指引`。

**第一轮（MOCK 视觉/交互验证）**：页面渲染、console 无报错、核心交互、响应式断点、设计系统 token 抽样、关键页面截图归档（作为 P6 材料）。

**第二轮（接口对接后功能验收）**：重跑第一轮 + 网络请求校验（URL/Header/Payload 对齐后端 VO/Operate）+ 数据流验证（创建 `Long`/更新删除 `Boolean`/分页字段解析）+ 异常路径（错误码/超时的 toast 与 loading 态）+ 权限/多租户隔离（如适用），并**生成验收测试用例 Markdown**：

```markdown
## 验收测试用例
### TC-1: [正常路径]   前置条件 / 操作步骤 / 预期结果
### TC-2: [边界情况]   （最大长度、空列表、单条、大量分页）
### TC-3: [异常场景]   （接口报错、网络断开、权限不足）
### TC-4: [多租户/权限隔离]（如适用）
```

**出口**：编译/构建/自测全通过；前端任务测试用例 Markdown 已生成

---

## P6：开发者 Review

**执行者**：开发者 | **AI 暂停等待**

### ARCH 架构级 —— 深度评审

AI 输出完整 Review 材料：

```
## Review 材料（ARCH 架构级）
### 变更摘要        [文件清单 + 关键设计决策 + 为什么这样设计]
### 架构影响        [受影响的业务域/模块/契约，与既有架构的关系]
### AI Review 报告  [P4 逐维度结论 + 回溯扫描结果 + api-contract-checker 结果]
### P5 自测结果     [编译/preview 验证摘要 + 截图（前端）]
### 测试用例        [P7 验收清单]
### 需要决策        [AI 不确定、需开发者拍板的项]
---
请逐项审阅。通过 → 进入 P7；有问题 → 描述，我修复后重走 P4。
```

前端任务保持两轮（视觉 Review → 功能 Review），门禁同 YAPD 约定：开发者明确说"视觉通过"才对接接口，明确说"功能通过"才进 P7。

### NORMAL 常规级 —— 知会式确认

AI 输出精简摘要（10 行内）：

```
## 变更知会（NORMAL 常规级）
- 变更：[一句话 + 文件数]
- 自审：P4 reviewer 全维度通过 / 回溯扫描 [N] 处同类已处理
- 自测：[编译/preview 结论]
- 风险：[无 / 一句话]
---
过目后任意回复即视为确认（如需深度 Review 请说"升级 ARCH"）。
```

开发者**任意明确回复**（"OK"/"继续"/"知道了"）即过；超出摘要外的疑问或要求 → 升级为 ARCH 深度评审。

**门禁**：开发者未回复前不得进入 P7/P8。

---

## P7：开发者测试

**执行者**：开发者 | **AI 协助调试**

- 仅在前端对接完毕、可在页面上操作时进行；纯后端任务跳过 → P8
- **NORMAL 级**：开发者可回复"免测"跳过
- AI 输出测试指引：启动方式（项目 CLAUDE.md 的命令）+ P5 生成的 TC-N 测试用例 + 验收条件

**门禁**：开发者明确说"通过"后进 P8。发现 Bug → AI 修复 →（含回溯扫描）→ 重走 P4-P7。

---

## P8：开发者确认

**执行者**：开发者 | **硬门禁**

```
Review 通过 + 测试通过。确认提交代码？（确认/否）
```

开发者明确说"确认"/"提交"/"OK"后才执行 P9-P11。不通过 → 回退 P6。
NORMAL 级在 P6 知会确认中合并完成，不再二次询问。

---

## P9：更新进度（硬门禁）

**执行者**：AI | **关联 skill**：`progress-tracker`

1. `.document/plan/` 对应模块文档勾选完成任务（`- [ ]` → `- [x]`），同步文档状态与"最后更新"日期
2. **更新 `STATUS.md` 台账**：本需求条目迁移到对应状态（`已完成` 则移入已完成区），记录完成日期
3. 模块全部完成时更新 `00-plan-overview.md` 阶段状态

> **"完成"的定义包含本阶段**：台账与计划文档未更新，不得向开发者宣布任务完成。这是并行开发下其他会话判断进度的唯一依据。

**出口**：计划文档 + 台账已同步

---

## P10：沉淀核对

**执行者**：AI + 开发者 | **关联 skill**：`team-memory`、`capability-registry`

全程沉淀（规则 1）的**收尾核对**，逐项回答：

```
## 沉淀核对清单
- [ ] 本次开发者的纠正是否已全部写入 memory？（规则 1 应已即时完成，此处核对）
- [ ] 本次是否产出可复用能力（组件/工具/Flow/模式）？→ 登记 CAPABILITY.md；
      跨项目通用的 → 标记"待反哺 framework"
- [ ] 本次 P6/P7 被捕获的 AI 漏检是否已记入对应 reviewer 漏检史？
- [ ] 踩坑/架构决策/技术约束/契约变更是否需要新 memory 或 ADR？
- [ ] 既有 memory 是否因本次开发而过时？→ 更新或删除
```

向开发者输出核对结果，询问"还有需要补充沉淀的吗？（无则跳过）"

**出口**：核对完成

---

## P11：提交代码

**执行者**：AI | **关联 skill**：`git-commit`

1. `git status` + `git diff` 确认变更
2. **需开发者授权方可提交**；授权（含笼统的"允许 / 提交吧"）默认走 `git-commit` 分支流程
3. **分支门禁**：`git rev-parse --abbrev-ref HEAD` 确认当前分支
   - 已在开发分支（`{feat|opt|fix}/{yyyy.MM.dd}-{business}`）→ 原地提交
   - 在主干 → **从当前主干切开发分支**（如 `feat/2026.08.18-edit-password`）再提交
   - **主干直提**：仅当开发者本次明确说"允许直接从主干提交"；**单次有效，下次必须重问，禁止自主判断**
4. 前后端仓库各自独立提交、**分支名一致**；`.document/` 变更（台账/报告/memory）随同提交
5. 按 `git-commit` skill 编写 message：**feat / opt / fix 三分法**（scope 可选），多类型按 `feat → opt → fix` 分段；
   commit 与分支名中**禁止任何 AI 记号**（无 `Co-Authored-By` / `Generated with` / 模型名）
6. `git push -u origin {分支名}` → 输出交接四项（分支 / 提交 / 推送 / 待办：请自行合并主干）；
   **AI 不合并主干、不开合 PR/MR、不 force push**
7. 提交后 `git status` 确认干净

---

## P12：总结成果

**执行者**：AI | **关联 skill**：`dev-output`

按 `dev-output` 输出报告到 `.document/developer/output/{yyyy-MM-dd}_{stage}_{slug}.md`（与台账条目同名），随代码提交。

## 流程控制

### 回退规则
