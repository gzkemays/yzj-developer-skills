# 项目能力登记册（capability-registry）

> 解决两个长期痛点：① 已有能力在后续迭代中被忽视，开发者不提醒就重复造轮子；
> ② 核心业务能力散落在代码里，没有一处可检索的清单。
> 登记册不替代代码，它是**复用入口**：先查册，再写码。

---

## 一、登记册位置与结构

```
.document/developer/capability/
└── CAPABILITY.md          # 唯一登记册（前后端 + 业务能力统一维护，按节分区）
```

```markdown
# {项目名} 能力登记册

> 开发前必查：新功能涉及的能力是否已存在？最后更新：{yyyy-MM-dd}

## 后端 — 通用组件 / 工具
| 能力 | 位置 | 用途与边界 | 登记日期 |
|------|------|-----------|----------|
| TransactionUtils.asyncExecuteAfterCommit | support/utils/ | 事务提交后异步执行（RPC/MQ 防悬挂） | 2026-05-xx |

## 后端 — 业务流程（Flow / Job / Listener）
| 能力 | 位置 | 用途与边界 | 登记日期 |

## 后端 — API 模式 / 既有接口
| 能力 | 位置/路径 | 用途与边界 | 登记日期 |

## 前端 — 通用组件
| 能力 | 位置 | 用途与边界 | 登记日期 |
| SearchCard | components/common/search-card.vue | 列表页高级筛选卡片（@search/@reset） | 2026-05-xx |

## 前端 — 工具 / Hooks / Store 模式
| 能力 | 位置 | 用途与边界 | 登记日期 |

## 业务能力（跨端的完整功能单元）
| 能力 | 入口 | 说明（含哪些子能力、扩展点在哪） | 登记日期 |
| RAG 检索注入 | AiReportFlow + RedisVectorStore | 文档/会话向量化→检索→注入 LLM；扩展点：metadataFields | 2026-05-xx |

## 待反哺 framework
| 能力 | 通用化要点 | 提出日期 | 状态 |
```

**「用途与边界」必须写清**：它解决什么、不解决什么、有什么前置条件——让 AI 读一行就能判断"本次能不能用它"。

## 二、开发前必查（dev-session P2）

新需求进入开发前，按以下顺序检查：

1. 读 `CAPABILITY.md`，按**功能语义**（不只是字面关键词）匹配本次涉及的：组件、工具、流程、接口
2. 命中 → 在开发计划中明确"复用 {能力}"并标注扩展方式（直接用 / 加参数 / 包一层），**禁止平行再造**
3. 部分命中（已有能力覆盖 60% 以上场景）→ 优先扩展既有能力，扩展后更新登记行的"用途与边界"
4. 未命中但直觉上"这么基础的东西应该有"→ 再用 Grep 扫一遍代码确认（登记册可能漏登），确认后才新建
5. 向开发者汇报：`可复用：{清单}；需新建：{清单}`

> 判断口径：**新建一个与既有能力高度相似的东西，需要在计划中向开发者说明"为什么不复用"**。说不出理由就复用。

## 三、开发后登记（dev-session P10）

每次开发收尾核对：本次产出中是否有**复用价值**的内容？

### 登记标准（命中任一即登记）

- 第二个调用方出现了（或可预见会出现）的组件/工具/方法
- 完整解决一类业务场景的流程（Flow / 编排 / 跨端链路）
- 一套被验证可行的模式（API 设计模式、状态管理模式、集成方案）
- 脚本与自动化（数据修复、批量处理、校验工具）

### 登记动作

1. 在对应分区追加一行（能力 / 位置 / 用途与边界 / 日期）
2. 更新登记册顶部"最后更新"日期
3. **跨项目通用性判断**：与具体业务解耦、换个项目也能用的 → 同时登记到「待反哺 framework」区

### 不登记

- 一次性的业务页面/接口（属于功能本身，plan 文档已记录）
- 未经使用验证的"预留"能力（YAGNI）

---

## 四、反哺 framework 共享库

「待反哺 framework」区的条目按以下流程处理（迭代间歇或开发者发起）：

1. **通用化改造**：去掉项目专有命名/路径/业务假设，补充使用说明
2. **归位**：
   - 流程/方法论类 → framework `skills/.claude/skills/` 新建或合入既有 skill
   - 后端规范/模式类 → framework `skills/backend/` 对应 skill
   - 前端规范/组件模式类 → framework `skills/frontend/` 对应 skill
3. 提交到 framework 仓库（commit message：`feat(capability): 反哺 {能力} from {项目}`）
4. 登记册中该条目状态改为 `已反哺 → framework {路径}`

> framework 是团队的"总能力池"——新项目引入即获得全部历史沉淀。反哺率是衡量项目沉淀质量的指标。

---

## 五、登记册卫生

- 能力重构/迁移后**当场更新**位置与边界描述；删除的能力移除登记行
- 每次迭代结束（或月度）扫一遍：位置失效的行（文件已不存在）→ 修正或删除
- 登记册超过 100 行后按分区拆分文件（`CAPABILITY-backend.md` 等），主文件保留索引
